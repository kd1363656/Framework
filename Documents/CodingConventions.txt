1.省略形の名前について=======================================================================================================================================
・省略形の名前を書く際はすべて大文字にする(jsonのキー文字には適用しない)
{
	アッパーキャメルケースの場合
	PCH
	WindowCONFIG;

	ロウワーキャメルケースの場合
	pch
	windowCONFIG;
}
2.ヘッダーについて===========================================================================================================================================
・アッパーキャメルケースで書くこと
{
	理由 : 統一感がでてファイル全体が見やすくなる

	例↓
	ConverterBase.h
}
3.ヘッダーのインクルードについて=============================================================================================================================
・.cppや.hでインクルードをする必要が出てきた場合ファイルの先頭で行うこと
{
	理由 : ヘッダーファイルをインクルードする必要があるということは、その定義を使う必要があるということ
	先頭でインクルードしないと確実に定義をすべての関数やクラス内に渡すことができないから。

	例↓
	#include "Device.h"
	#include "Application.h"

	Device::Device()
	{
		Application::GetInstance().Execute();
	}
}
・プリコンパイル済みヘッダーではインクルードしたものが関係の深いものなら隣接して#include文を書き
そうでなければ1行、行間を開けて書く。
コメントでインクルードしているものについて書く
{
	理由 : 何をインクルードしているのか分かりやすいようにするため、
	コメントは索引として書く

	例↓
	// Windows
	//================================================
	// Windows
	//================================================
	#define NOMINMAX
	#include <Windows.h>
	#include <wrl/client.h>
	#include <cassert>
	
	//================================================
	// STL
	//================================================
	#include <string>
	#include <filesystem>
	#include <fstream>
	#include <limits>
	#include <unordered_map>
	#include <thread>
	#include <vector>
	#include <queue>
	#include <algorithm>
	#include <memory>
}
・リンカーは一番下に書くこと
{
	理由 : インクルードとリンカー設定の違いがはっきりして見やすいから

	例↓
	//================================================
	// フレームワーク
	//================================================
	#include "Framework/Framework.h"

	//================================================
	// リンカー設定
	//================================================
	#pragma comment(lib, "winmm.lib")
}
4.変数の書き順について=======================================================================================================================================
※注意 : 今から上からの条件が優先順位が高く下に行くにつれて優先順位が下がっていくものとする
・記憶域指定子の記述順
{
	inline static
	inline
	static
	記憶域指定子なし
}
・const修飾子の記述順
{
	constexpr
	const
	const修飾子なし
}
・配列かどうかでの記述順
{
	複数値を保持する型  (std::arrayなど(隣り合う配列の記述順は型別記述順を参照))
	例↓

	std::array<double> m_arrayA = {};
	std::array<int>    m_arrayB = {};

	単一の値を保持する型(intなど)
	int m_a = 0;
}
・参照、ポインタ、値の記述順
{
	int& 参照 
	int* ポインタ
	int  値
}
・型別記述順
{
	型エイリアスは各型の後に記述順位がつくものとする
	例↓

	using I_N_T = int;

	int m_int     = 0; // TypeAliasなし
	I_N_T m_i_n_t = 0; // TypeAliasあり

	型別大まかな優先順位は外部定義、自身定義、stdコンテナ定義、型エイリアス

	右に行くにつれて定義優先順位が弱い
	クラス、構造体、Enum、std::型、組み込み型(double、float、unsigned long long、unsigned int、int、bool、void(外部のTypeAlias, 自身のTypeAlias, stdコンテナのTypeAlias))
}
5.変数の命名規則について=====================================================================================================================================
・定数はk_
{
	例↓
	static const int k_num = 4;
}
・メンバ変数はm_
{
	例↓
	class Hoge final
	{
	public:
		
		 Hoge() = default;
		~Hoge() = default;
	
	private:
		
		int m_a = 0;
	}
	
	struct HogeHoge final
	{
		int m_dataA = 0;
	}
}
・ローカル変数はl_
{
	例↓
	const Hoge l_hoge = {};
}
・引数はa_
{
	例↓
	class Hoge final
	{
		 Hoge(const int a);
		~Hoge();
	}
}
6.変数の書き方について=======================================================================================================================================
・const修飾子と型の位置を合わせない
{
	もしconst 修飾子を持つ変数とそうでない変数を行間なしにくっつけて書く場合
	型の位置をconstに合わせるのではなくconstの後ろに続く型に合わせる
	理由 : そうしたほうがconstなのかそうでないかが一目でわかるから
	例↓
		  int   l_numA  = 0;
	const auto& l_hogeA = HogeA::GetInstance();
}
・隣接する同じ型同士ならキーと格納する型の書く位置を揃える
{
	例↓
	std::unordered_map<int,         std::string> l_mapA = {};
	std::unordered_map<std::string ,std::string> l_mapB = {};
}
・クラスや構造体の初期化にはUniformInitialization(波括弧初期化)を使う
{
	例↓
	Hoge l_hoge = {};
}
・ポインタの場合は明示的にnullptrを代入する
{
	例↓
	Hoge* l_hoge = nullptr;
}
・後ろconstがある変数ととない変数が行間なしで並んでいる場合揃えない、後ろconstがあるもの同士が隣接するならは揃える
{
	例↓
	const TypeInfo* const  k_baseInfo;
	const std::string_view k_name;

	const TypeInfo*         const k_baseInfo;
	const std::string_view* const k_name;
}
・組み込み型の場合floatなどで定義、そうでないクラスや構造体などで型を明示する必要がなければautoで定義
名前が長いunsigned intなどもauto定義
{
	例↓
	const auto& l_typeInfo = GetTypeInfo<T>();
	const auto& l_string   = GetName       ();
	
	float l_num = 0.0F;
}
・配列の[]の位置を揃える
{
	例↓
	l_indexListA  [3] = 1ULL;	
	l_indexListB_B[2] = 1ULL;	
}
・定義
{
	絶対に行間を開ける
	例↓
	const std::uint32_t l_index = 
	{
		0ULL
	};
}
・論理演算子使う場合は改行する(assertは除外)
{
	例↓
	      bool l_isB    = true;
	      bool l_isC    = true;
	const bool l_result = l_isB &&
						  l_isC;
}
・ビット演算子を使う場合
{
	3つ以下なら改行しない
	例↓
	const int l_num = 11 & 1;

	4つ以上なら改行して縦に並べる
	理 : 演算子が縦に並ぶことでフラグの数と内容が一目で分かるから
	例↓
	const int l_flags = flagA |
						flagB |
						flagC |
						flagD;
}
・符号の位置は合わせる
{
	理 : 条件文が!(false)の時かtrueの時かが瞬時にわかりやすいため
	※符号ありの数値の符号の後の数字と、符号なしの数値の数字の位置を揃える
	　符号なしの数値は符号分のスペースを空けておく

	例↓ 変数宣言の場合
	int a_num1 =  1;	
	int a_num2 = -1;

	例↓ 初期化リスト内の場合
	Vector3 l_direction = {  0.50F, -1.0F,  0.50F };
	Vector3 l_color     = {  1.0F,   1.0F,  1.0F };
}

7.関数について===============================================================================================================================================
・関数の引数はデフォルト引数を使わない限り変数の書き順を参照すること
・隣接する関数で戻り値の後にスペーシングを挟んで関数名を書く場合は一番長い戻り値型に合わせる
{
	理 : 戻り値型と関数名の区切りが揃うことで可読性が高まるから
	※隣接する関数同士にのみ適用し、離している関数には適用しない
	例↓ 隣接する場合
	const boost::uuids::uuid*        FindPTRAssetUUID        (const std::filesystem::path& a_assetFilePath) const;
	const Struct::AssetFilePathData* FindPTRAssetFilePathData(const boost::uuids::uuid&    a_uuid)          const;

	例↓ 離している場合(合わせない)
	void Deserialize(const nlohmann::json& a_rootJson);

	nlohmann::json Serialize() const;
}
・隣接する関数で引数がある場合は引数の位置を合わせる
{
	理 : 引数の型と名前が縦に揃うことで対応関係が一目で分かるから
	基本ルール : 第一引数の型の先頭位置を合わせ、その後に続く引数名の先頭位置も一番長い型に合わせる

	例↓
	const boost::uuids::uuid*        FindPTRAssetUUID        (const std::filesystem::path& a_assetFilePath) const;
	const Struct::AssetFilePathData* FindPTRAssetFilePathData(const boost::uuids::uuid&    a_uuid)          const;

	※constの位置、型の位置、引数名の位置、)の位置、末尾constの位置がすべて揃っている
}
・もし使う関数が行間を開けていなければ()の位置を合わせる
{
	理 : ()の位置が揃うことで関数呼び出しの境界が一目で分かるから
	基本ルール : 関数名が長い方の()の位置に合わせてインデントする

	例↓
	auto& l_application = Application::GetInstance();

	l_application.Execute       ();
	GraphicsManager::GetInstance().Execute();

	関数呼び出し全般も同じく関数名が長い方の()に合わせる
	理 : 隣接する呼び出しの()が揃うことで一覧性が高まるから
	例↓
	l_graphicsManager.INIT ();
	l_physicsManager.INIT  ();
	l_audioManager.INIT    ();

	l_sceneManager.EarlyUpdate   ();
	l_sceneManager.Update        ();
	l_sceneManager.LateUpdate    ();
	l_sceneManager.PostLateUpdate();

	ローカル変数でゲッターを使う場合も同じく関数名が長い方の()に合わせる
	理 : 隣接するゲッター呼び出しの()が揃うことで一覧性が高まるから
	例↓
	auto& l_physicsManager  = FWK::Physics::PhysicsManager::GetInstance  ();
	auto& l_graphicsManager = FWK::Graphics::GraphicsManager::GetInstance();
	auto& l_editorManager   = FWK::Editor::EditorManager::GetInstance    ();
	auto& l_audioManager    = FWK::AudioManager::GetInstance             ();
	auto& l_sceneManager    = FWK::SceneManager::GetInstance             ();
	auto& l_inputManager    = FWK::InputManager::GetInstance             ();

	変数名の長さが異なる場合も()の位置は関数名が長い方に合わせる
	例↓
	      auto& l_inputManager       = FWK::InputManager::GetInstance         ();
	const auto& l_keyboardController = l_inputManager.GetREFKeyboardController();

	※.cppでのそのクラスの関数定義には適用しない
	理 : 関数定義はクラス名修飾が付き名前が長くなるうえに
	1関数につき1定義なので整列の意味が薄いから
	例↓ (.cppの関数定義は()の位置を合わせない)
	void Application::CanUpdateFrame() const
	{
		～処理～
	}
	void Application::UpdateWindowTitleBar() const
	{
		～処理～
	}
}
・関数の記述優先順位について
{
	例↓
	大まかな処理順を優先
	void Init  ();
	void Load  ();
	void Create();

	void Update();

	アップデートなどで使用する関数をあとは書いていく
	void UpdateName();

	Set処理と何らかの処理をする場合
	(Applyじゃないものを採用してもよい)
	void Apply(int a_num) const;

	セッターはわざわざ名前を変えなくていい
	変数をセットするのみの関数
	理由 : 関数のオーバーロード機能が使えるから
	void Set(int a_num) const;

	値を取得してくる処理(あとはFindなど(Findだけじゃなくてよい))
	const std::string& FetchREFName(int a_index) const;
	const std::string* FetchPTRName(int a_index) const;

	std::string& FetchMutableREFName(int a_index);
	std::string* FetchMutablePTRName(int a_index);

	std::string FetchVALName (int a_index) const;

	// 変数の取得のみの関数
	const Hoge& GetREFHoge() const;
	const Hoge* GetPTRHoge() const;

	Hoge& GetMutableREFName();
	Hoge* GetMutablePTRName();

	Hoge GetVALName() const;
}
・特殊なメソッド名の命名(省略形はすべて大文字にするルールに従う)
{
	理由 : ライフサイクル系のメソッドは名前で役割を一目で判別できるようにするため

	例↓
	// 初期化処理(InitializeではなくINIT)
	void INIT();

	// コンフィグの読み込み・保存・読み込み後処理(CONFIGはすべて大文字)
	void LoadCONFIG    ();
	void SaveCONFIG    () const;
	void PostLoadCONFIG();

	// フレームの開始・終了(処理フローの両端なので離す)
	void BeginFrame();

	void EndFrame();

	// 更新系(処理順を意識して整列させる)
	void EarlyUpdate   ();
	void Update        ();
	void LateUpdate    ();
	void PostLateUpdate();
}
・同じような処理を持つ関数があるならば行間を開けずに書く(ゲッターやセッターは除外)
{
	例↓
	void HogeA  ();
	void HogeA_A();
}
・行間を開けていないかつ引数がある関数ならば引数の位置を合わせる
{
	例↓
	void Hoge (int    a_a, int a_b);
	void HogeB(double a_b);
}
・隣接する関数同士ならば戻り値の後に続くメソッド名を合わせる
{
	理由 : 戻り値とメソッド名に区切りがついて見やすくなるから
	例↓
	void        HogeA(int      a_a, int a_b);
	std::string HogeB(HogeHoge a_hoge);
}
・関数の引数が4個以上なら改行する
{
	void RequestSpriteDraw(const Math::Vector2&      a_pos,
						   const Math::Vector2&      a_scale,
						   const Texture&            a_texture,
						   const Struct::SpriteRect* a_sourceRect = nullptr,

・関数ので四個以上の引数があり改行してるものがあれば
似たような処理でも定義側は離して定義する
.cppでは似ているような処理の関数同氏は隣接させる
{

						   const Struct::SpriteRect* a_sourceRect = nullptr,

	{
		～処理～
	}

	void RequestModelDraw(const Struct::ModelResource& a_modelResource, const Math::Matrix& a_worldMatrix)

	}

・関数の使用をする際に関数を呼び出す際の()の位置を合わせない
{
	例↓
	m_hwnd = CreateWindow(a_windowClassName.c_str(),

8.クラスについて=============================================================================================================================================
・クラスの書き方(基底、派生、どちらでもないクラスに共通する部分)
{
	class Hoge
	{
	private:

		std::unordered_mapなどの宣言が長くなってしまうものに使うこと
		using HogeStringMap = std::unordered_map<std::string, std::string>;

		そのクラスでしか使わない構造体、クラス、Enum、型エリアリアスはprivate指定子でで一番上に定義
		理由 : そのクラスでしか使わない定義を外部に公開する意味がないしそうすることで保守性が高まるから
		例↓
		
		class HogeHoge
		{
			 HogeHoge() = default;
			~HogeHoge() = default;
		}

		struct StructHoge
		{
			int a = 0;
		}

	public:

		コンストラクタの書き方
		
		なにも引数などを使わないコンストラクタの場合はクラス名の位置を合わせる
		理由 : ~の位置が分かりやすくなり一瞬でコンストラクタ・デストラクタを見分けることができるから
		 Hoge() = default;
		~Hoge() = default;
		

		引数などを使うコンストラクタの場合は定義だけ書いてcppで記述
		動作を書くその場合デストラクタもcppに書く
		コンストラクタでは変数を隣接する場合(同じ型int型が2行連続して並ぶなど)()の位置を合わせる
		理 : 見やすいから
		
		 Hoge(const int a_num1, int a_numB2) : 
			m_num1 (a_num1),
			m_numB2(a_numB2),
		 {}
		~Hoge();
		
		関数の記述優先順位を参照して関数を書く

	private:

		コンストラクタ初期化を行わない場合メンバイニシャライザを使って初期化する
		コンストラクタ初期化ならコンストラクタでメンバを初期化する
		理由 : コンストラクタを使用するクラスなのかそうでないクラスなのかが初期化の仕方でわかるから

		・コンストラクタ初期化（メンバイニシャライザ）を行う場合は全メンバをコンストラクタ初期化すること
		.hでのインライン初期化とコンストラクタ初期化を混在させない
		理由 : どちらで初期化されているかが不明確になり、二重初期化になるから

		例↓
		
		コンストラクタがDefaultの場合.h
		int m_a = 0;
		
		コンストラクタが.hで定義のみの場合の.cpp
		Hoge(const int a_a) : 
			m_a(a_a)
		{}
		Hoge() = default;

		privateアクセス指定子の書き順
		理 : 変数より関数を見る機会がデバックの時に多いからprivateの上あたりに
		あったほうが見やすいと思ったから 
		関数の記述優先順位を参照して関数を書く

		マクロをクラス内部で使用する場合は一番下で書くこと
		理由 : マクロでアクセス指定子を変えている可能性があるから 
	}
}
・クラスの書き方(基底クラス
{
	ほとんどの場合は継承しないクラスと同じ
	例↓
	class HogeHoge
	{
	public:
		
		指定子とコンストラクタ、仮想デストラクタが分かりやすいように
		コンストラクタ、デストラクタの名前の位置を合わせる
		         HogeHoge() = default;
		virtual ~HogeHoge() = default;
	}
)
・継承するクラス
{
	もし継承が最後なら必ずfinalをつける
	理由 : 今回のゲーム制作は一人だが、もし複数人で組むのならということを想定して
	finalを書いておくとこれ以上継承してほしくないクラスということがコンパイラがエラーを出してくれるので
	分かりやすいからfinalをつける
	ほとんどの部分は継承しないクラスと同じ
	例↓
	class HogeHoge final : public Hoge
	{
	public:

		1.必ずデストラクタにoverrideを記述する
		基底クラスのデストラクタがvirtual定義されているかどうかを調べるため
		 HogeHoge()          = default;
		~HogeHoge() override = default;

		2.基底クラスの仮想関数の振る舞いを変える場合
		virtual定義を基底クラスでされているかどうかを確認するためoverrideを書いておく
		void Hoge() override;
	}	
}
・シングルトンのクラス
{
	ほとんどの部分は継承しないクラスと同じ
	シングルトンを安全に利用するための基底クラスを継承する
	例↓
	class Hoge final : public SingletonBase<Hoge>
	{
	private:

		1 : シングルトンのためのコンストラクタ定義をする際は
		そのクラスでしか使わない構造体、クラス、Enum、型エイリアスと同じ位置
		(privateアクセス指定子の一番上)にコンストラクタ、デストラクタを書くこと
		理 : structやenum、usingと同じくクラスの定義の一部として先頭に置くことで
		そのクラスがシングルトンであることが一目で分かるから

		フレンドクラスにしないと基底クラスのSingletonBaseがprivateアクセス指定子にアクセスできず
		コンパイルエラーになるから
		friend class SingletonBase<Hoge>;

		 Hoge() = default;
		~Hoge() = default;

	public:

		関数の記述優先順位を参照して関数を書く

	private:

		int m_a = 0;
	}
}
9. .cppについて==============================================================================================================================================
・ヘッダーファイルのインクルードは一番上で行う
{
	理 : ヘッダーは構造体などの定義の情報を有しているので一番上で定義しないと定義を
	使えない可能性があるから
	例↓
	.cppの記述
	#include "Application.h"
		
	Application:s:Application() = default;
}
・処理内容が近しい関数同士は関数の間に改行を開けずに隣接させる
{
	理 : 関連する処理のまとまりが一目で分かるから
	例↓
	void Hoge::PreUpdate()
	{
		～処理～
	}
	void Hoge::Update()
	{
		～処理～
	}

	処理内容が異なる関数の間は改行を開ける
	void Hoge::Execute()
	{
		～処理～
	}

	void Hoge::LoadCONFIG()
	{
		～処理～
	}
}
・処理フローの両端に位置する関数は似ていても離す
{
	理 : Deserialize → 何らかの処理 → Serialize のように
	処理フローの両端に位置する関数は間に別の処理が挟まるため
	隣接させると処理の流れが誤解されるから

	例↓ 離すべき例
	void Hoge::Deserialize()
	{
		～処理～
	}

	void Hoge::SomeProcess()
	{
		～処理～
	}

	void Hoge::Serialize() const
	{
		～処理～
	}

	例↓ 隣接させるべき例(連続して呼ばれる処理)
	void Hoge::LoadCONFIG    ()
	{
		～処理～
	}
	void Hoge::PostLoadCONFIG()
	{
		～処理～
	}
}
・.hで隣接させた関数は.cppでも同じく隣接させる
{
	理 : ヘッダーと実装ファイルで配置の一貫性を保つことで
	定義を確認する際に対応関係が一目で分かるから

	例↓ .h
	void PreUpdate();
	void Update   ();

	void Execute();

	例↓ .cpp
	void Hoge::PreUpdate()
	{
		～処理～
	}
	void Hoge::Update()
	{
		～処理～
	}

	void Hoge::Execute()
	{
		～処理～
	}
}
・ファイルの最終行に改行を入れない
{
	理 : 不要な空行ができるのを防ぐため
	例↓
	class Hoge final
	{
		～処理～
	};
	←改行なしで終わる
}
10.return文について=========================================================================================================================================
・基本的に何もせずにreturnだけするなら一行で書き終える
{
	例↓
	if (!GetTypeInfo<Type>()) { return; }
}
・処理をしてreturnするなら改行する
{
	例↓
	if (!GetTypeInfo<Type>()) 
	{
		処理
		return;
	}
}
・連続してif分を書く、それがreturn分の場合()の位置を揃える
{
	if      (m_isA)  { return false; }
	else if (m_isAB) { return false; }
}
・jsonの場合
{
	例↓
	return nlohmann::json
	{
		{ a_key.data(), l_typeINFO->k_name.data() }
	};
}
11.if文について=============================================================================================================================================
・改行なしでreturn用のif文を書く場合
{
	例↓
	if (!GetTypeInfo<Type>()) { return; }
}
・改行ありでreturn用のif文を書く場合
{
	例↓
	if (TypeInfo* l_typeInfo = GetTypeInfo<Type>();
	l_typeInfo!) 
	{
		return; 
	}
}
・論理演算子をif文内部で使うなら改行すること
{	
	bool l_isA = true;
	bool l_isB = true;

	if (l_isA &&
		l_isB)
	{
		...諸々の処理
	}
}
・ローカル変数で再利用しないboolを使う場合if-initstatementを使用する
2つ以上の変数を使うならif-initstatementは使わない
{
	例↓
	if (TypeInfo* l_typeInfo = GetTypeInfo<Type>();
	l_typeInfo!) 
	{
		return; 
	}
	
	bool l_isA = true;
	bool l_isB = true;

	if (l_isA &&
		l_isB)
	{
		...諸々の処理
	}
}
・if文の中では()の位置は合わせない
{
	例↓
	if (Application.Create() &&
		Graphics.Create())
	{
		...諸々の処理
	}
}
・符号の位置を合わせる
{
	理 : 条件文が!(false)の時かtrueの時かが瞬時にわかりやすいため
	例↓

	bool l_isA  = true;
	bool l_isBA = true;
	bool l_isC  = true;

	if ( l_isA  && 
		!l_isBA &&
		 l_isC)
	{
		...諸々の処理
	}
}
12.名前空間について=========================================================================================================================================
・ルート名前空間はFWKとする(FWKは省略形なのですべて大文字)
・サブ名前空間はアッパーキャメルケースで書く
・C++17のネストされた名前空間構文(namespace FWK::Sub)を使う
{
	理由 : 短く書けて可読性が高まるから

	例↓
	namespace FWK::Graphics
	{
		class GraphicsManager final : public Utility::SingletonBase<GraphicsManager>
		{}
	}

	// 実際に使われているサブ名前空間の例
	// FWK::Graphics, FWK::Editor, FWK::Converter, FWK::Constant, FWK::Concept,
	// FWK::Utility, FWK::TypeAlias, FWK::Struct, FWK::Enum, FWK::TypeTrait
}
・前方宣言だけの場合はnamespace FWK {}で分けて書く
{
	例↓
	namespace FWK
	{
		class GameObject;
	}
}
13.クラス・構造体・Enum・コンセプト・型エイリアスの命名について=============================================================================================
・クラス・構造体はアッパーキャメルケース
{
	・基底クラスにはBase接尾辞をつける
	例↓ ComponentBase, MatrixStrategyBase, SingletonBase, BinaryConverterBase, EditorWindowBase

	・管理クラスにはManager接尾辞をつける
	例↓ GraphicsManager, EditorManager, AudioManager, SceneManager

	・Json変換クラスにはJsonConverter接尾辞をつける(Iはつけない)
	例↓ AudioManagerJsonConverter, GraphicsManagerJsonConverter, GameObjectJsonConverter

	・継承させないクラスには必ずfinalをつける
	例↓ class Application final, class CameraComponent final, class Device final

	・構造体もfinalをつける
	例↓ struct StringHash final, struct TypeINFO final
}
・Enumはenum classで定義し、列挙子はアッパーキャメルケース
{
	例↓
	enum class WindowStyle
	{
		None,
		Normal,
		BorderlessFullScreen,
	};
}
・コンセプトはIs〜Conceptという命名にする
{
	例↓ IsDerivedBaseConcept, IsSmartPTRConcept, IsDerivedComponentBaseConcept, IsDerivedEditorWindowBaseConcept
}
・型エイリアスはアッパーキャメルケース
{
	例↓
	using HogeStringMap = std::unordered_map<std::string, std::string>;
	using FactoryMap    = std::unordered_map<std::string, std::function<Type()>>;
	using BaseType      = typename Type::element_type;
}
14.マクロについて=============================================================================================================================================
・マクロ名はFWK_プレフィックスをつけ、アッパースネークケースで書く
{
	理由 : マクロであることが一目でわかり、名前の衝突を防ぐため

	例↓
	#define FWK_DEFINE_TYPE_INFO(Derived, Base)
	#define FWK_DEFINE_TYPE_INFO_ROOT(Derived)
	#define FWK_REGISTER_FACTORY_METHOD(FactoryType, DerivedType)
	#define FWK_ADD_LOG(TextColor, Format, ...)
	#define FWK_ASSERT_RETURN_IF(Condition, Message)
	#define FWK_JSON_SERIALIZE_ENUM(EnumType, ...)
}
・クラス内部で使用するマクロは一番下に書くこと(アクセス指定子を変える可能性があるため)
{
	例↓
	class Hoge final
	{
	private:

		int m_a = 0;

		FWK_DEFINE_TYPE_INFO(Hoge, HogeBase)
	};
}
15.定数の修飾子について=======================================================================================================================================
・クラススコープの定数はstatic constexprを使う
・名前空間スコープの定数はinline constexprを使う
・ファイルパスなど実行時に決まるものはinline static constを使う
・定数名はk_プレフィックス(変数の命名規則を参照)
{
	例↓
	// クラススコープ
	static constexpr float k_cameraDefaultFOVYDegree = 60.0F;

	// 名前空間スコープ
	namespace FWK::Constant
	{
		inline constexpr float k_cameraDefaultFOVYDegree = 60.0F;
	}

	// ファイルパス
	inline static const std::filesystem::path k_configFileIOPath = "CONFIG/Graphics/GraphicsCONFIG.json";
}
16.ブレース(波括弧)の位置について=============================================================================================================================
・関数・クラス・制御文の開きブレースは改行して次の行に書く(Allmanスタイル)
{
	例↓
	void Hoge::Execute()
	{
		if (l_isA)
		{
			...
		}
	}

	class Hoge final
	{
	public:
		 Hoge() = default;
	};
}
