================================================================================
 FWK コーディング規約
================================================================================

このプロジェクトのソースコード(C++ / HLSL)を書くときの決まりごとをまとめたものです。
新しくコードを書くときや既存のコードを直すときは、この規約に合わせてください。
ここに書かれていないことは、同じフォルダ・同じ役割を持つ既存のクラスに合わせてください。


================================================================================
 第1章 基本ルール
================================================================================

1-1. ヘッダー(.h)にはコメントを書きません。説明が必要な内容は .cpp 側に書きます。
     ・コメントを書いてはいけないのは「関数の外側」です。
       クラス・構造体・列挙型・定数・メンバ変数・関数の宣言(シグネチャ)の前後や行末には、コメントを書きません。
     ・テンプレートや inline のように、そのヘッダーに処理の本体を書かなければならない関数の「中」は例外です。
       .cpp と同じように、処理にコメントを書きます(第16章 16-4 / 16-8)。
       それ以外のもの(.cpp に書けるもの)の中身を、コメントを書くためにヘッダーへ書くことはしません。
1-2. .h / .cpp ともに、ファイルの最後の行の後ろには改行を入れません。
1-3. 構造体を class の public に入れ子で定義しないでください。
     ・そのクラスの中だけで使う構造体は private に入れ子で定義します。
     ・外部(呼び出し側)でも使う構造体は Source/Framework/Definition/Struct/<分類>/XxxStruct.h に
       namespace FWK::Struct で定義します(詳しくは第14章 14-3)。
1-4. スマートポインタを引数で受け取るときは、次のように使い分けます。
     ・参照するだけの場合は const std::weak_ptr<T>& で受け取ります。
     ・所有を共有・保持する場合(リストに格納する、寿命を延ばすなど)は const std::shared_ptr<T>& で受け取ります。
1-5. ファイルを追加したときは、次の3箇所に必ず登録してください。
     ・Framework.vcxproj         : <ClInclude Include="Source\..."/> / <ClCompile Include="Source\..."/>
     ・Framework.vcxproj.filters : <Filter Include="Source\..."> の定義と、各ファイルの <Filter>Source\...</Filter>
       フィルターの名前と階層は、実際のフォルダとまったく同じにします(親のフィルターも定義します)。
       ファイルやフォルダを移動したときは、vcxproj・filters・Framework.h のパスも、同時に更新します。
     ・Source/Framework/Framework.h : 依存関係の順番に合う位置に #include


================================================================================
 第2章 ファイル形式
================================================================================

2-1. 文字コードは BOM 付きの UTF-8 にします(HLSL も同じです)。
2-2. ファイルの末尾には改行を入れません。
2-3. 改行コードは CRLF にします。
2-4. インデントは半角スペース4つです。タブは使いません。
2-5. 行末に空白を残さないでください。
2-6. 1行の文字数に上限は設けていません。縦揃えを優先した結果、行が長くなるのは問題ありません。


================================================================================
 第3章 フォルダとファイル名
================================================================================

3-1. 1つのクラスにつき1つのファイルを作り、ファイル名はクラス名と同じにします。
     ・大文字・小文字も含めて、完全に同じにします(MainMenuBarEditor.h。MainMenubarEditor.h とは書きません)。
     ・クラス名を変えたとき、またはファイル名が違っていたときは、ファイル名をクラス名に合わせ、
       vcxproj・filters・Framework.h・.cpp の #include も同時に直します(第1章 1-5)。
         CameraPassConstantBufferUploader.h → CameraPassDynamicConstantBufferUploader.h(クラス名に合わせる)
     ・Definition のファイルは、中身が1つだけでも <クラス名>Constant.h / <クラス名>Enum.h のように種別を付けます。
         Definition/Enum/Editor/Splitter/EditorWindowPaneSplitterEnum.h
       型エイリアスのファイルも同じで、ファクトリーの別名は XxxFactoryTypeAlias.h にします。
         Definition/Type/Alias/Factory/Shared/EditorWindowSharedFactoryTypeAlias.h
     ・Framework.h などに書く #include のパスも、ファイル名と大文字・小文字まで同じにします。
       Windows では大文字・小文字が違っていてもビルドが通るため、ファイル名を変えたときは include も必ず確認します。
         NG : #include "Editor/MainMenu/MainMenubarEditor.h"
         OK : #include "Editor/MainMenu/MainMenuBarEditor.h"
3-2. .h と .cpp は同じフォルダに置きます。テンプレートやインライン関数だけのクラスは .h のみで構いません。
3-3. フォルダは「機能 / 下位機能」の階層で分けます。付属クラスは役割ごとのサブフォルダに置きます。
       Converter/Json/      XxxJsonConverter
       Converter/Binary/    XxxBinaryConverter
       Inspector/           XxxInspector
       Buffer/Constant/     XxxDynamicConstantBufferUploader
       Builder/ Loader/ Record/ Mode/ Popup/ Shortcut/ Clipboard/ Selection/ Factory/ など
     ・同じ種類のものが複数あるときは、種類のフォルダの下に、対象ごとのフォルダを作って分けます。
         Graphics/Render/Graph/Pass/Debug/Physics/  PhysicsDebugPass
         Graphics/Render/Graph/Pass/Debug/Editor/   EditorDebugPass(PhysicsDebug / EditorDebug と横に並べません)
     ・1つのファイルのためだけの下位フォルダは作りません。同じ機能のフォルダにそのまま置きます。
         Graphics/Render/Camera/CameraContext.h(Camera/Context/ の下には置きません)
     ・UndoRedo のコマンドは、ウィンドウの下ではなく Editor/Command/<対象>/<操作>/XxxCommand.h に置きます。
         Editor/Command/GameObject/Create/CreateGameObjectCommand.h
         Editor/Command/GameObject/Destroy/DestroyGameObjectCommand.h
       GameObject の下位の対象(コンポーネント)も、同じ形で GameObject の下に置きます。
         Editor/Command/GameObject/Component/Add/AddGameObjectComponentCommand.h
         Editor/Command/GameObject/Component/Remove/RemoveGameObjectComponentCommand.h
     ・コマンドは、操作を終えてから EditorUndoRedoSystem::PushUndoCommand<XxxCommand>(...) で履歴へ積みます。
       履歴へ積む場所は、操作を行う関数の中の1箇所だけにします。
     ・Undo で位置(並び順)を元に戻すコマンドは、添字(index)をメンバに持ちません。
       変更前と変更後の「親の UUID」と「兄弟の UUID の並び」を記録し、Undo / Redo のときに UUID から並びを組み直します。
       リストの内容が多少変わっていても位置がずれず、範囲外の添字によるエラーも起きません。
         Struct::ReparentGameObjectState(m_parentUUID / m_siblingUUIDList)
         Utility::FetchVALReparentGameObjectState / Utility::ApplyGameObjectSiblingOrder
     ・削除したオブジェクトを Undo で戻すコマンドは、実体を std::shared_ptr で持ちます。
       UUID と JSON から作り直す方法は、手間と処理時間がかかるためです(CreateGameObjectCommand / RemoveGameObjectComponentCommand)。
       持たせるのは実体だけで、追加先の GameObject・親・並び順は、これまでどおり UUID で持ちます。
     ・1回の操作で複数のコマンドが必要なときは、既存のコマンドをメンバに持つコマンドにまとめて、1回の Undo で戻せるようにします。
         PasteCutGameObjectCommand(CreateGameObjectCommand と DestroyGameObjectCommand をメンバに持ちます)
3-4. 定数・列挙型・構造体などの定義は Source/Framework/Definition/ にまとめます。
     ファイル名は「その定義を使うクラスの名前」に種別を付けたものにします。
       Definition/Constant/<分類>/<クラス名>Constant.h   namespace FWK::Constant
       Definition/Enum/<分類>/<クラス名>Enum.h           namespace FWK::Enum
       Definition/Struct/<分類>/<クラス名>Struct.h       namespace FWK::Struct
       Definition/Type/Alias/XxxTypeAlias.h               namespace FWK::TypeAlias
       Definition/Concept/.../XxxConcept.h                namespace FWK::Concept
       Definition/Macros/.../XxxMacros.h
     関連する定義であれば、1つのファイルに複数書いて構いません。
3-5. 汎用的な関数は Utility/<分類>/XxxUtility.h に inline 関数として書きます(namespace FWK::Utility)。
     ・複数のクラスや関数から使う処理だけを Utility にします。
         Utility::CollectDescendantGameObjectList(CreateGameObjectCommand と Operation から使います)
     ・1つのクラスの中でしか使わない処理は、そのクラスの private の関数として書きます。
         WorldOutlinerEditorWindowGameObjectOperation::FetchVALDestroyedGameObjectRecord
     ・複数のクラスが同じ「持たせる処理」(キャッシュなど、状態を持つもの)を使う場合は、
       Utility/<分類>/<動作>/ に XxxHelper クラスとして書き、使う側のクラスのメンバに持たせます(namespace FWK::Utility)。
       inline 関数ではなく、状態を持つため、クラスにします。
         Utility/GameObject/Fetch/Component/Transform/FetchSelfGameObjectTransformComponentHelper
         (自身のGameObjectのTransformComponentを PostDeserialize で weak_ptr にキャッシュする。
          GameObjectCameraComponent が m_fetchSelfGameObjectTransformComponentHelper として持つ)
3-6. シェーダーのファイル名は <名前>_<ステージ>.hlsl(AS / MS / PS / VS / CS)にします。共通部分は .hlsli に書きます。


================================================================================
 第4章 #include と PCH
================================================================================

4-1. ヘッダーの先頭には #pragma once だけを書きます。
4-2. ヘッダーには #include を書きません(PCH.h と Framework.h は除きます)。
     必要な型はすべて Framework.h が依存関係の順に include します。
4-3. Framework.h は依存関係の順(Constant → Enum → Struct → TypeAlias → Converter → 本体のクラス …)に並べます。
     大きな区切りには次のバナー(= は79個)を使い、小さな区切りは「// 見出し」の1行で書きます。
         //===============================================================================
         // 見出し
         //===============================================================================
4-4. PCH.h は強制インクルードされています。外部ライブラリのヘッダーは PCH.h に追加してください。
4-5. .cpp では自分のヘッダーだけを include します。
         #include "XxxClass.h"
     Application.h が必要な場合だけ、2行目に相対パスで追加します。
         #include "../../Application/Application.h"
4-6. ヘッダー内で前方宣言が必要な場合は、本体とは別の namespace ブロックに書いて先頭に置きます。

         #pragma once

         namespace FWK
         {
             class GameObject;
         }

         namespace FWK::Editor
         {
             class XxxClass final
             {
             ...


================================================================================
 第5章 名前空間
================================================================================

5-1. 名前空間はネスト記法で1つのブロックにします。using namespace は使いません。
         namespace FWK::Graphics
         {
         }
5-2. 名前空間は次のように使い分けます。
       FWK              GameObject / Scene / Asset / Audio / Input / Window などの中核部分
       FWK::Editor      エディター
       FWK::Graphics    描画
       FWK::Physics     物理
       FWK::Converter   すべての XxxJsonConverter / XxxBinaryConverter
       FWK::Utility     汎用的な関数・クラス
       FWK::Constant / FWK::Enum / FWK::Struct / FWK::TypeAlias / FWK::Concept / FWK::TypeTrait
5-3. .cpp では namespace ブロックを書かず、完全修飾名で定義します。戻り値の型も完全修飾で書きます。
         void FWK::Graphics::PhysicsDebugPass::Execute(...)
         FWK::TypeAlias::StorageID FWK::Utility::StorageIDAllocator::Allocate()
         std::shared_ptr<FWK::GameObject> FWK::GameObject::Clone(...) const
5-4. 関数の中では FWK:: を省略し、Graphics:: / Constant:: / Utility:: のように書きます。
     FWK の外にある Application だけは FWK:: から書きます。


================================================================================
 第6章 命名規則
================================================================================

6-1. 変数には次のプレフィックスを付けます。プレフィックスの直後は lowerCamelCase で書きます。
       ローカル変数     l_xxx
       引数             a_xxx
       メンバ変数       m_xxx (構造体のメンバにも付けます)
       定数             k_xxx (static constexpr / inline constexpr / const メンバ)
       HLSL の cbuffer のメンバ・groupshared 変数   g_xxx
     プレフィックスの直後に来る語は、略語であっても小文字で書きます。
       m_srvDescriptorIndex / m_cbCameraPass / k_maxMeshletVertexCount
     ・関数の中で宣言する constexpr の変数は、定数でもローカル変数なので l_ を付けます(k_ ではありません)。
         constexpr auto l_kind = TypeTrait::PTRType<PayloadType>::k_kind;
     ・Undo / Redo 用に「変更前」「変更後」の値を組で持つ変数は、before / after を先頭に置きます。
       bool の場合も before / after の後ろに Is を続けます(is で始まらなくても構いません)。
         m_beforeName / m_afterName / m_beforeIsSceneSelected / m_afterIsSceneSelected
6-2. 型と関数の名前は次のとおりです。
       クラス / 構造体 / 列挙型 / 関数    PascalCase
       列挙型の値                         PascalCase (enum class のみ使います)
       テンプレート引数                   Type、または XxxType (ComponentType / DerivedType / FactoryType など)
                                          値のテンプレート引数も XxxType にします(CommandType / HeapType)
                                          Argument / Value のように Type で終わらない名前は使いません(ArgumentType / ValueType)
                                          可変長引数は Args(template <typename... Args>。class... とは書きません)
       Concept                            IsXxxConcept / IsDerivedXxxConcept
       マクロ                             FWK_ + 大文字のスネークケース (FWK_ASSERT_RETURN_IF など)
       基底クラス                         XxxBase (インターフェースだけは I を付けます: ICommand)
       型エイリアス(using)                XxxMap / XxxList / XxxSharedFactory / XxxUniqueFactory
6-3. 名前の付け方
     ・コンテナの変数名は種類に合わせます。
         vector / deque / array → XxxList、unordered_map → XxxMap、unordered_set → XxxSet、queue → XxxQueue
         ImVector などの外部ライブラリの配列も XxxList にします(m_textLineOffsetList)。
         XxxToYyy の形の名前でも、最後に種類を付けます(m_uuidToAssetFilePathDataMap)。
         std::span は、配列の一部を指す「範囲」なので XxxRange にします(a_elementRange / l_vertexRange)。
         char の配列を文字の入力欄として使うものは XxxBuffer / XxxText で構いません(m_inputBuffer)。
     ・bool は is / can / should / was / has で始めます(m_isDestroyed / m_canAutoScroll / m_shouldUpdateMatrixDirty)。
       引数・ローカル変数も同じです。contains / requires / use などの動詞で始めず、言い換えます。
         l_containsRoot → l_hasRoot / l_requiresFolderTreeRefresh → l_shouldRefreshFolderTree /
         a_updateCurrentFolderPath → a_shouldUpdateCurrentFolderPath / m_useMAXX → m_shouldUseMAXX
       引数の値の意味を名前で表すための bool の定数は、この限りではありません(k_advanceWritePosition / k_useMINSide)。
       bool の初期値の定数は k_initialIsXxx の形にします(k_initialIsActive / k_initialIsSuccess)。
     ・イテレータは l_xxxITR とします。l_itr のように中身の分からない名前にはしません。
       xxx には、検索したコンテナの名前から m_ / l_ / a_ と List / Map / Set を除いたものを使います。
         m_prefabMap.find(...)        → l_prefabITR
         m_folderOpenStateMap.find()  → l_folderOpenStateITR
       範囲を順にたどるイテレータは l_cursorITR にします(for (auto l_cursorITR = l_startITR; ...))。
     ・名前の綴りを間違えないようにします。英単語は略さずに書き、略語は 6-6 の一覧のものだけを使います。
         Pos → Position(l_cursorPositionY)/ Settingss・Removeal・Movig などの綴りの誤りは書きません
     ・役割を持つクラスは「持ち主の名前 + 役割」をつなげた名前にします。
         AssetBrowserEditorWindowFolderPane / GameObjectTransformComponentInspector / GameObjectJsonConverter
       役割を表す語: Manager(シングルトン) System Context Registry Storage Record Builder Loader Extractor
                     Uploader Converter Inspector Pane PopupDrawer ShortcutHandler Clipboard SelectionState
                     Operation Creator DrawRequest Pass Mode Command Helper
6-4. 関数名の付け方
     ・取得関数(Getter)は次の3種類を使います。単なる Get は使いません。
         const auto& GetREFXxx() const { return m_xxx; }    const 参照を返す
         auto& GetMutableREFXxx() { return m_xxx; }          変更可能な参照を返す
         auto GetVALXxx() const { return m_xxx; }            値を返す(bool / float / weak_ptr などは型を明示します)
     ・取得関数の名前は、Get(REF / Mutable / VAL)の後ろに、返す変数名または型名をそのまま付けます。
       Active / Current / Main などの用途や状態を足した別名の取得関数は作りません。
       「どの値を返すか」を切り替える必要が出たら、同じ名前の取得関数の中身で切り替えます。
         OK : const auto& GetREFRenderGraphFrameResource() const { return m_renderGraphFrameResource; }
         NG : const auto& GetREFActiveRenderGraphFrameResource() const { return m_renderGraphFrameResource; }
       変数名の一部を省いたり、別の語に変えたりもしません。
         OK : GetREFClipboardFilePathList() { return m_clipboardFilePathList; }
         NG : GetREFFilePathList        () { return m_clipboardFilePathList; }
         NG : GetVALMaxSlopeAngleRadius () { return m_maxSlopeAngleRadians; }
       メンバ変数の名前が m_num / m_size のように短すぎる場合は、メンバ変数のほうを m_descriptorNUM のように直します。
     ・まだ使う場所がない取得関数・設定関数は作りません。使う処理を実装するときに、必要な分だけ足します。
     ・設定関数(Setter)の引数名は必ず a_set にします。
         void SetXxx(const float a_set) { m_xxx = a_set; }
         void SetXxx(const std::string& a_set) { m_xxx = a_set; }
         void SetXxx(Struct::GPUResource&& a_set) { m_xxx = std::move(a_set); }
     ・Fetch は、計算や探索を伴う取得関数で、.cpp に実装するものに使います。
         FetchVALXxx / FetchPTRXxx / FetchREFXxx / FetchMutablePTRXxx
       Fetch / Find の後ろには、必ず VAL / PTR / REF などの返し方を付けます。
         NG : FetchIcon / FetchVertexUV / FindUniqueComponent
         OK : FetchVALIcon / FetchVALVertexUV / FindVALUniqueComponent
     ・Find はコンテナからの検索に使います。
         FindPTRXxx (見つからなければ nullptr) / FindMutablePTRXxx / FindVALXxx (weak_ptr や値) / FindXxxITR (イテレータ)
     ・Generate は生成に使います(GenerateVALUUID など)。
     ・Is / Can / Has は bool を返す判定に使います。
       bool を返す判定の関数は、必ず Is / Can / Has のどれかで始めます。
       Contains / Exists / Check などの動詞では始めず、Has に言い換えます(6-3 の bool の変数と同じ考え方です)。
         NG : bool Contains(const boost::uuids::uuid& a_uuid) const; / bool ContainsAssetUUID(...) const;
         OK : bool Has     (const boost::uuids::uuid& a_uuid) const; / bool HasAssetUUID     (...) const;
       処理の成否を返す関数(Create / Load / Setup / EnableDebugLayer など)は判定ではないため、この限りではありません。
     ・Apply は、値を設定するとともに関連する状態(Dirty フラグなど)も更新する処理に使います(ApplyTransformPosition)。
     ・Setup は GPU へのバインドや初期設定に使い、Set とは区別します。
     ・Try は失敗する可能性がある処理で、bool を返します(TryReadBinaryData)。
     ・XxxIfNeeded は条件を満たしたときだけ実行する処理に使います(LoadNextSceneIfNeeded)。
     ・よく使う動詞: Create Apply Draw Add Deserialize Serialize Setup Clear Handle Release Calculate
                     Load Save Build Register Remove Collect Process Transition Convert Extract Sweep Select Toggle
6-5. ライフサイクルに関わる関数は次の名前に揃えます。
       INIT / LoadCONFIG / PostLoadCONFIG / Deserialize / PostDeserialize / Create
       EarlyUpdate / Update / LateUpdate / PostLateUpdate / BeginFrame / Execute / EndFrame
       Draw / EditInspector / Serialize / SaveCONFIG / Release
6-6. 識別子の途中に入る略語は大文字で書きます。
       REF VAL PTR ITR INIT CONFIG INFO UUID ID NUM MIN MAX RECT
       SRV UAV RTV DSV CBV CB VB GPU CPU FPS FBX UFBX IMGUI MIP LOD HWND IO OP FUNC STR
     例: GetREFTypeINFO / FindPTRPrefab / l_cursorITR / k_invalidStaticTypeID / k_defaultSpriteRECTX
         SaveCONFIG / k_imguiDebugINFOColor / FetchVALCPUDescriptorHandle / k_fovYDegreeMAX
         DeserializeDepthStencilOPDesc / k_defaultMIPLevels / k_executeListNUM / l_baseJsonPTR / a_targetRECT
     ・MIN / MAX は、識別子の途中では必ず大文字にします。プレフィックスの直後は 6-1 のとおり小文字です。
         CalculateWorldMAXScale / k_defaultMINPrimaryPaneSize / k_maxCharacterVirtualMAXSlopeAngleRadians
       D3D12 の構造体のメンバ(ResourceMinLODClamp)や Jolt のメンバ(mMaxSlopeAngle)など、外部ライブラリの名前はそのまま使います。
     ・Json は常に Json と書きます(JsonKey / JsonConverter)。
     ・Diff は Diff と書きます(SerializeDiff / DetectJsonDiff)。
     ・ImGui は、プレフィックスの直後では imgui / imGui(k_imguiAccentColor / m_imGuiSRVDescriptorIndexMap)、
       関数名・型名・識別子の途中では IMGUI(IMGUIDelayedTooltip / AllocateIMGUISRVDescriptorIndex /
       IMGUISRVDescriptorIndexMap / m_previewIMGUISRVDescriptorIndexList)と書きます。


================================================================================
 第7章 ヘッダー(クラス宣言)の書き方
================================================================================

7-1. クラスの修飾
     ・派生させないクラスには final を付けます。基底クラス(XxxBase)には付けません。
     ・構造体にも final を付けます。
     ・継承は public 継承で書きます: class Xxx final : public XxxBase
7-2. アクセス指定子
     ・public → private の順に書きます。
     ・シングルトンや private の using を持つクラスは、private(using / friend / コンストラクタ)→ public → private の順にします。
     ・protected は必要なときだけ、public と private の間に書きます。
     ・アクセス指定子の前後には必ず空行を入れます。
     ・friend は、シングルトンの基底クラス(Utility::SingletonBase)を継承するクラスだけに使います。
         friend class SingletonBase<XxxManager>;
       それ以外の目的では friend を使いません。他のクラスから呼ぶ関数は public にします。
       ※注意 : namespace FWK::Physics の中に friend class Scene; と書くと、FWK::Scene ではなく、
                存在しない FWK::Physics::Scene を指すことになり、何の効果もありません。
7-3. public の宣言は次の順に並べます。
       コンストラクタ / デストラクタ
       コピー・ムーブの禁止
       INIT
       Deserialize → PostDeserialize → Create
       EarlyUpdate / Update / LateUpdate / PostLateUpdate / BeginFrame / Execute / EndFrame
       Draw / EditInspector
       Serialize
       その他の処理関数 (Clone / Add / Remove / Convert / Request / Prepare / Handle など)
       Is / Can / Has
       Apply
       Set
       Fetch / Find (この2つの間の順番は決めていません)
       GetREF
       GetMutableREF
       GetPTR
       GetMutablePTR
       GetVAL
       public の static constexpr 定数
     ・同じアクセス指定子(public / protected / private)の中では、処理関数 → Is / Can / Has → Apply → Set → Fetch / Find →
       GetREF → GetMutableREF → GetPTR → GetMutablePTR → GetVAL の順に、上から下へ並べます。
       取得関数・設定関数・判定関数(Is / Can / Has)の後ろに、処理関数を書きません。
         NG : Find... の後ろに Set... を書く / GetREF... の後ろに Fetch... や Has... を書く / Apply... や Is... の後ろに Add... などの処理関数を書く
       アクセス指定子で区切られていれば、別のグループとして扱います(private の処理関数を public の GetREF... より下に書いてよい)。
       並びを合わせるためだけに、アクセス指定子を増やしません。
     ・Deserialize / Load は処理フローの最初、Serialize / Save は最後に行う処理なので、隣り合わせにせず、必ず空行を入れて離します。
         bool LoadTextureAsset(const std::filesystem::path& a_filePath, DirectX::ScratchImage& a_scratchImage, DirectX::TexMetadata& a_texMetadata);

         bool SaveTextureAsset(const DirectX::ScratchImage& a_scratchImage, const std::filesystem::path& a_filePath);
     ・.cpp の関数の定義も、ヘッダーで宣言した順に書きます(第8章 8-2)。
7-4. private の宣言は次の順に並べます。
       private 関数 → static constexpr 定数(k_) → メンバ変数(m_) → 型情報マクロ
     ・定数は型ごとにまとめ、型が変わるところで空行を入れます。
     ・メンバ変数は「配列 → ポインタ → オブジェクト → Converter / Inspector → データ → 列挙型 → 数値 → bool」の順に並べます(第20章)。
7-5. コンストラクタとデストラクタ
     ・コンストラクタの前に半角スペースを1つ入れて、デストラクタの ~ と位置を揃えます。
           XxxClass() = default;
          ~XxxClass() = default;
     ・基底クラスの場合は次のように揃えます。
                   XxxBase() = default;
          virtual ~XxxBase() = default;
     ・派生クラスでは override を付け、= の位置を揃えます。
           XxxClass()          = default;
          ~XxxClass() override = default;
     ・特別な初期化がなければ = default にします。
     ・コピーやムーブを禁止するときは4行をセットで書き、const の有無で位置がずれないように揃えます。
          XxxClass(const XxxClass&)           = delete;
          XxxClass(      XxxClass&&) noexcept = default;

          XxxClass& operator=(const XxxClass&)           = delete;
          XxxClass& operator=(      XxxClass&&) noexcept = default;
7-6. メンバ変数の初期化
     ・コンストラクタを = default にするクラスは、すべてのメンバ変数を宣言の位置で初期化します(既定メンバ初期化子)。
         クラス / 構造体 / コンテナ / weak_ptr   = {}
         shared_ptr / unique_ptr / ComPtr        = nullptr
         数値 / bool / 列挙型                    名前付きの定数で初期化します
                                                 = k_initialXxx / = Constant::k_defaultXxx
                                                 bool は = false か定数を使い、= true は直接書きません
                                                 列挙型は = Enum::XxxType::Invalid
     ・コンストラクタで初期化するクラス(引数を受け取るなど、= default ではないコンストラクタを書くクラス)は、
       すべてのメンバ変数を、.cpp のコンストラクタの初期化子リストで初期化します。
       この場合、メンバ変数の宣言には既定メンバ初期化子(= {} など)を書きません。
       一部のメンバだけを初期化子リストに書き、残りを既定メンバ初期化子にする、という混ぜ方はしません。
         m_beforeName(a_beforeName),
         m_afterName (a_afterName),

         m_gameObjectUUID(a_gameObjectUUID)
     ・初期化子リストは、メンバ変数の宣言順に書き、種類が変わるところで空行を入れ、( の位置を揃えます(第8章 8-4)。
       受け取る値がないメンバも、省略せず m_xxx() と書いて初期化します。
7-7. インライン実装
     ・Getter / Setter は1行で書きます: { return m_xxx; } / { m_xxx = a_set; }
     ・戻り値の型を auto にしてよいのは、ヘッダーに本体を書く Getter(GetREF / GetMutableREF / GetVAL)だけです。
       Fetch / Find など .cpp に本体を書く関数は、戻り値の型を必ず書きます(本体が見えない所から呼ぶと型が決まらずコンパイルできないため)。
     ・空の仮想関数の本体には決まった文を書きます。
         virtual void Xxx() { /*必要に応じてオーバーライドしてください*/ };
     ・テンプレート関数・テンプレートクラスの本体はヘッダーに書きます。
     ・使わない引数は名前を省略します。
         void Execute(const ResourceContext&, Renderer& a_renderer, RenderGraph& a_renderGraph) override;
7-8. 縦揃え(表のように揃えます)
     ・続けて並ぶ宣言は、関数名の後ろの ( の位置を揃えます。
          void EarlyUpdate   () const;
          void Update        () const;
          void LateUpdate    () const;
          void PostLateUpdate() const;
     ・引数も型・名前・末尾の const が縦に並ぶように揃えます。
     ・Getter / Setter のまとまりやメンバ変数のまとまりも、型名や = の位置を揃えます。

     ・空行を入れずに上下で隣り合う関数は、似た処理の関数だけにします。似ていない関数との間には空行を入れてグループを分けます。
         似ている例  : Undo と Redo / Add と Remove / BeginFrame・Execute・EndFrame /
                       INIT・Deserialize・PostDeserialize・Create / 同じ動詞で始まる関数(DrawCard と DrawCardIcon)
         似ていない例: CanUpdateFrame と UpdateWindowTitleBar(判定と更新) / DrawMenuFile と UpdateShortCutKey(描画と更新)
7-9. クラスの最後には型情報マクロを書き、ファクトリーへの登録は namespace の外に書きます。
          namespace FWK::Graphics

          FWK_REGISTER_FACTORY_METHOD(FWK::TypeAlias::RenderGraphPassUniqueFactory, FWK::Graphics::FinalColorPass)

       継承しないクラスには FWK_DEFINE_TYPE_INFO_SINGLE(Xxx) を使います。
     ・登録マクロの引数は完全修飾名で書きます。
7-10. シングルトンは Utility::SingletonBase を継承して、次の形で書きます。

7-11. 構造体
     ・namespace FWK::Struct に struct Xxx final で定義し、メンバには m_ を付けて宣言の位置で初期化します。
     ・構造体は継承しません(Xxx final : public YyyBase のような構造体の継承は書きません)。
       共通部分と派生を持つものは、専用のクラス(XxxBase と派生クラス)にして、private のメンバと GetREF / GetMutableREF で公開します。
     ・既定値の定数は、構造体の中に static constexpr k_initialXxx / k_defaultXxx として置きます。
     ・GPU の定数バッファ用は CBXxx、頂点用は VBXxx という名前にします。

7-12. 1つの機能は複数の小さなクラスに分けます。

 第9章 書式

9-1. 波括弧は Allman スタイルで、独立した行に書きます。
9-2. if / for / while / switch の後ろには半角スペースを1つ入れます: if (
9-3. if / for / while の本体には、必ず {} を付けます。
     ・本体が return または continue の1文だけの場合は、1行で書いて構いません。
       break の1文だけの場合を含め、それ以外の本体は、必ずブロックで書きます。

         if (l_inDegreeList[l_nodeIndex] != k_emptyInDegree) { continue; }
9-4. else は } の次の行に書きます。} else とは書きません。

9-5. && や || を含む条件は1行に1条件ずつ書き、演算子は行末に置いて、条件を縦に揃えます。

             l_component->GetVALIsDisable())
         {

         }
     return 文や代入の右辺でも同じように書きます。

     条件が2つだけの短い場合や、本体が return だけの1行 if の場合も、1行にまとめずに改行します。
     条件の行どうしでは、関数呼び出しの ( の位置は揃えません(条件の先頭だけを揃えます)。
     行末の && / || の前は半角スペース1つにします。演算子の位置を縦に揃えるための空白は入れません。
         NG : if (l_uuid.is_nil()                    ||

         OK : if (l_uuid.is_nil() ||
                  m_componentUUIDRegistry.Has(l_uuid) ||
         if (ImGui::IsKeyDown(ImGuiKey_LeftCtrl) &&

         FWK_ASSERT_RETURN_VALUE_IF(!m_hullShader &&
                                    m_domainShader,
     && / || を含む式は、関数の引数に直接書きません。先に bool の変数へ受けてから渡します。
         NG : l_cameraContext.SetIsCullingBySceneCamera(l_viewportEditorWindow && l_viewportEditorWindow->GetVALIsDrawCulledResult());

                                                    l_viewportEditorWindow->GetVALIsDrawCulledResult();

              l_cameraContext.SetIsCullingBySceneCamera(l_isCullingBySceneCamera);
9-6. if の初期化文は ; の後で改行し、条件を ( の次の位置に揃えます。

9-7. 引数の改行
     ・宣言では、引数が3個以下なら1行で書き、4個以上なら1行に1引数ずつ書いて名前の位置を揃えます。
       引数が3個以下のときに改行して並べることはしません(引数そのものが複数行になるラムダや && / || の条件は除きます)。
       const が付かない引数は「const 」の6文字分を空けて、型の位置を揃えます。
         void DeserializeScene(const nlohmann::json&              a_rootJson,
                               const nlohmann::json&              a_baseJson,
                               const SceneGameObjectPrefabSystem& a_prefabSystem,
                                     Scene&                       a_scene);
     ・呼び出しも同じで、3個以下なら1行、4個以上なら1行に1引数ずつ書き、2行目以降は ( の次の位置に揃えます。
         l_directCommandList.DrawInstanced(static_cast<UINT>(l_lineVertexList.size()),
                                           k_lineInstanceCount,
                                           k_startVertexLocation,
                                           k_startInstanceLocation);
     ・3個以下でも、引数の中に複数行にわたる条件がある場合は1行に1引数ずつ書きます。
     ・引数が2~3個のときは、式が長くなっても改行して並べません。長すぎる場合は、先に変数へ受けてから渡します。

                     l_io.MouseDelta.y * m_rotateSpeed);
         OK : Rotate(l_io.MouseDelta.x * m_rotateSpeed, l_io.MouseDelta.y * m_rotateSpeed);
     ・FWK_ASSERT の条件に長い関数呼び出しを書く場合も同じです。結果を bool の変数に受けてから、1行で書きます。

     ・続けて並ぶ代入や初期化は、= の位置を揃えます。
     ・続けて並ぶ関数呼び出しは、( の位置を揃えます。
         m_hierarchy.INIT    ();

         const auto& l_hierarchy = l_gameObject->GetREFHierarchy();
         const auto& l_parent    = l_hierarchy.GetREFParent     ().lock();

         l_rootSlotList.emplace_back(l_i);

         auto& l_physicsManager  = FWK::Physics::PhysicsManager::GetInstance  ();
         auto& l_graphicsManager = FWK::Graphics::GraphicsManager::GetInstance();

         const auto  l_buttonWidth = std::min                    (k_addComponentButtonWidth, l_regionWidth);
     ・const 付きと const なしの宣言が並ぶときは、const なしの行を6文字下げて型の位置を揃えます。
               auto& l_gameObjectSelectionState = a_editorManager.GetMutableREFGameObjectSelectionState   ();
         const auto& l_cursor                   = l_gameObjectSelectionState.FindVALLastSelectedGameObject().lock();
     ・FWK_ASSERT が続くときは、メッセージの開始位置も揃えます。
     ・{ } の初期化子は、要素が4つ以上なら縦に並べ、3つ以下なら1行に書きます(色・座標・大きさなど、すべて同じです)。

9-9. 関数の中の空行
     ・return の前には空行を入れます(ブロックの最初の文が return の場合は除きます)。
     ・FWK_ASSERT の後には空行を入れます。FWK_ASSERT が続く場合は、詰めて並べます。
     ・1行で書いた if の後には空行を入れます。
       ただし1行の if が続くときは、間に空行を入れずに上下に詰めて並べ、{ の位置を縦に揃えます(最後の1行 if の後に空行を入れます)。

         if (a_modelMesh.m_indexList.empty())       { return false; }
         if (a_modelMesh.m_bonePaletteList.empty()) { return false; }

       間にコメントを書く場合は、コメントの前に空行を入れて、別のまとまりとして扱います。
     ・文の種類が変わるところ(宣言から呼び出しへ、代入から宣言へ など)には空行を入れます。
       同じ種類の文(宣言の連続、代入の連続、同じ関数の呼び出しの連続)は詰めてまとめます。
       変数の宣言が続くときは、型や const の有無、右辺の内容が違っても空行を入れずにまとめ、
       const なしの行を6文字下げて型と名前の位置を揃え、= と右辺の ( の位置も揃えます(9-8)。
         NG : const bool l_isSearching = IsSearching();

              float l_inputTextWidth = ImGui::GetContentRegionAvail().x;
         OK : const bool  l_isSearching    = IsSearching                 ();
                    float l_inputTextWidth = ImGui::GetContentRegionAvail().x;
     ・コメントの前には空行を入れます(ブロックの先頭は除きます)。
     ・関数の先頭と末尾には空行を入れません。
     ・空行は2行以上続けて入れません。関数の中・関数と関数の間・アクセス指定子の前後・#include の後も、空行は1行だけです。
9-10. switch は次のように書きます。

     ・case ごとに {} のブロックを作り、break; はブロックの後ろに case と同じ深さで書きます。

9-11. その他の記号
     ・& と * は型の側に付けます: Type& a_name
     ・型名を書いて値を作るときは、( ) ではなく { } を使います。
         NG : ImVec2(l_buttonWidth, k_autoFitButtonHeight)
         OK : ImVec2{ l_buttonWidth, k_autoFitButtonHeight }
       座標・色・大きさなどの値を表す型(ImVec2 / ImVec4 / 数学の型 / D3D12 や Jolt の小さな値の型)が対象です。
       { } の中は、3つ以下なら1行、4つ以上なら縦に並べます(9-8 と同じです)。
       { } は小数から整数への変換(縮小変換)をコンパイルエラーにしてくれるため、値の入れ間違いに気づけます。
       次のものは ( ) のままにします。
         ・std::vector / std::string など: { } だと「要素の並び」と解釈され、意味が変わります(std::vector<int>(5) と std::vector<int>{ 5 } は別物です)。
         ・static_cast<Type>(...) のような変換、関数の呼び出し
     ・テンプレートは template <typename Type> と書きます(< の前にスペースを入れ、class ではなく typename を使います)。
     ・#if はインデントせずに行頭に書き、#if defined(_DEBUG) の形にします。


================================================================================
 第10章 変数・型・リテラル
================================================================================

10-1. 関数の戻り値など、式の結果を受け取るローカル変数は auto を基本に使います。
     ・関数の戻り値は、値を返す関数であっても const auto& で受け取ります。
         const auto& l_nodeCount = a_dependencyList.size();
     ・後で変更する変数は auto / auto& を使い、ポインタは const auto* / auto* を使います。
     ・bool / float / int などは型を明示しても構いません: const bool l_isInserted = ...;
     ・8バイト以上の変数(std::size_t / UINT64 / double / 数学の型 / UUID / 文字列 / イテレータ / スマートポインタなど)は、
       後で変更しないのであれば必ず const auto& で受け取ります。値で受け取ることはしません。
         const auto& l_index        = static_cast<std::size_t>(a_defaultTextureType);
         const auto& l_assetDataITR = m_uuidToAssetFilePathDataMap.find(l_assetUUID);
       ただし、std::min / std::max のように引数の参照を返す関数に一時オブジェクトを渡した場合は、
       参照先が文の終わりで消えてしまうため値で受け取ります。
         const auto l_copySize = std::min(l_name.size(), l_bufferSize - k_lastOffset);
       また、元の値がこの後で変わったり消えたりするため、コピーを取っておく必要がある場合も値で受け取ります。
         // この後eraseするとイテレータが無効化されるため、要素をコピーしておく
         const auto l_moveData = *l_moveITR;
       変更前の値を残しておく変数(l_beforeName / l_oldPrefabUUID)、front() の後で pop する要素、
       この後で増やすメンバの値(m_nextStorageID)を受け取る変数も、同じ理由で値で受け取ります。
     ・auto&& は使いません。後で std::move する変数は auto で受け取ります。
         NG : auto&& l_rootJson = Utility::LoadJsonFile(a_filePath);
         OK : auto   l_rootJson = Utility::LoadJsonFile(a_filePath);
10-2. 変数の型名を書くか auto にするかは、右辺で型が決まっているかどうかで決めます。
     ・右辺がリテラル(0ULL / 1.0F / 0U など)の場合は、型がサフィックスでしか決まらないため、必ず型名を書きます。
         std::size_t l_bufferOffset = 0ULL;
         for (std::size_t l_nodeIndex = 0ULL; l_nodeIndex < l_nodeCount; ++l_nodeIndex)
       次のようには書きません。
         auto l_bufferOffset = 0ULL;
         for (auto l_nodeIndex = 0ULL; ...)
     ・右辺が型の決まっている変数・定数・関数の戻り値などの場合は、auto で構いません。
         auto l_number       = l_startNumber;
         auto l_adapterIndex = k_firstAdapterIndex;
         for (auto l_boneIndex = k_firstBoneIndex; l_boneIndex < l_boneCount; ++l_boneIndex)
       std:: の型(std::uint32_t / std::size_t / std::string / コンテナなど)やスマートポインタ
       (std::unique_ptr / std::shared_ptr / std::weak_ptr)も同じです。参照で受け取れる場合は const auto& で受け取ります。
     ・ヘッダーで定義するもの(定数・メンバ変数)は、右辺に関係なく必ず型名を書きます(10-7)。
     既定値で構築するときは Type l_xxx = {}; と書きます。
         nlohmann::json l_rootJson = {};
         std::vector<std::weak_ptr<GameObject>> l_displayedList = {};
10-3. 範囲 for は for (const auto& l_xxx : xxxList) と書き、要素を変更するときだけ auto& を使います。
     要素が8バイト以上の場合(std::size_t の添字リストなど)に const auto で受け取ることはしません。
     map は構造化束縛を使います: for (const auto& [l_key, l_value] : l_xxxMap)
10-4. 添字を使う for は for (std::size_t l_index = 0ULL; l_index < l_count; ++l_index) と書きます。
     リテラルで始める添字は、比べる相手に合わせて型名を書きます(UINT / std::uint32_t など)。auto l_index = 0ULL とは書きません。
     定数や変数で始める場合は auto で構いません: for (auto l_boneIndex = k_firstBoneIndex; ...)
     添字が不要な場合は範囲 for を使ってください。
10-5. リテラル
     ・float には大文字の F を付け、小数点も必ず書きます: 1.0F / 0.5F
     ・符号なし整数には大文字の U / UL / ULL を付けます: 0U / 0UL / 0ULL
     ・接尾辞は型に合わせます。std::size_t / UINT64 / std::uint64_t は ULL、UINT / std::uint32_t は U、DWORD は UL です。
     ・固定幅の整数型は、必ず std:: を付けて書きます(std::uint8_t / std::uint32_t)。uint32_t のように std:: を省きません。
       列挙型の基になる型も同じです: enum class XxxTag : std::uint8_t
10-6. マジックナンバーは書きません。0 や 1 であっても、意味が分かる名前の定数にします。
         k_noRemainder = 0U / k_halfMagnification = 0.5F / k_singleElementCount = 1ULL
         k_firstBoneIndex = 0ULL / k_invalidStorageID = std::numeric_limits<...>::max()
     数値を直接書いてよいのは、添字 for の開始値の 0 と、パディングの 0.0F だけです。
10-7. 定数の書き方
     ・ヘッダーで定義する定数・メンバ変数は、auto を使わず必ず型名を書きます: inline constexpr std::size_t k_xxx = 1ULL;(constexpr auto k_xxx とは書きません)
     ・そのクラスだけで使う定数は、クラスの private に static constexpr で書きます。
     ・複数のファイルで使う定数は、Definition/Constant に inline constexpr で書きます。
       namespace の中に static constexpr とは書きません(static はクラスの中の定数だけに使います)。
         NG : namespace FWK::Constant { static constexpr float k_epsilon = 0.000001F; }
         OK : namespace FWK::Constant { inline constexpr float k_epsilon = 0.000001F; }
     ・文字列の定数は static constexpr std::string_view で書きます。
     ・列挙型の値や、ImGui / D3D12 などが用意している定数(ImDrawFlags_None など)のためだけに、static constexpr の定数は作りません。
       使う場所で、その値をそのまま書きます。
         NG : static constexpr ImDrawFlags k_borderFlags = ImDrawFlags_None;
         OK : l_drawList->AddRect(l_min, l_max, l_color, k_rounding, ImDrawFlags_None, k_thickness);
     ・ファイルパスは inline static const std::filesystem::path k_configFileIOPath = "CONFIG/Xxx/XxxCONFIG.json"; と書きます。
     ・定数の名前は次の形をよく使います。
         k_defaultXxx / k_initialXxx / k_invalidXxx / k_emptyXxx / k_minXxx / k_maxXxx / k_xxxCount
         k_xxxJsonKey (JSON のキー) / k_xxxLabel (ImGui の表示文字列・ID) / k_editorName


================================================================================
 第11章 処理の組み立て方
================================================================================

11-1. 異常な場合は早めに return して(ガード節)、ネストを浅くします。
11-2. weak_ptr は関数の先頭で lock() し、有効かどうかを確認します。
         const auto& l_gameObject = a_gameObject.lock();

         if (!l_gameObject) { return; }
11-3. Deserialize 系の関数は、最初に if (a_rootJson.is_null()) { return; } と書きます。
11-4. 状況に応じて次のように使い分けます。
     ・通常の動作として起こりうる「対象がない」「対象外」     → 普通に return します。
     ・プログラムの誤りで、起きてはいけない状態              → FWK_ASSERT_RETURN_IF / FWK_ASSERT_RETURN_VALUE_IF を使います。
     ・処理は続けられるが知らせておきたい状態                → FWK_ADD_LOG(Constant::k_imguiDebugWarningColor, "...") の後に return します。
11-5. null の判定は !l_xxx と書きます。== nullptr や == true / == false は書きません。
11-6. キャストには static_cast を使います。必要な場合だけ reinterpret_cast / std::static_pointer_cast を使います。
     dynamic_cast は使いません。型の判定には TypeINFO の k_staticTypeID を使います。
11-7. インクリメントは前置(++l_xxx)で書きます。
11-8. ラムダ式
     ・ラムダ式は std の検索・並べ替えなどのアルゴリズム(find_if / any_of / erase_if / stable_sort など)に渡す述語としてだけ使います。
       それ以外の用途(変数に入れて呼び出す、処理のまとまりを分ける など)では使わず、関数にします。
       複数の関数から使うなら Utility、1つのクラスの中でだけ使うならそのクラスの private の関数です(第3章 3-5)。
         ラムダの中の処理が長くなる場合も、処理を関数にして、ラムダからはその関数を呼ぶだけにします。
           std::ranges::stable_sort(l_rootList,
                                    [&l_rankMap](const auto& a_left, const auto& a_right)
                                    {
                                        return FetchVALGameObjectSiblingRank(l_rankMap, a_left) < FetchVALGameObjectSiblingRank(l_rankMap, a_right);
                                    });
     ・キャプチャは [&l_gameObject] / [this] / [] のように明示します。[&] や [=] は使いません。
     ・ラムダの引数にも a_ を付けます。
     ・ラムダを引数として渡すときは改行し、{ を [ の位置に揃えます。
         std::erase_if(m_selectedGameObjectList,
                       [&l_gameObject](const auto& a_selectedGameObjectWeak)
                       {
                           return a_selectedGameObjectWeak.lock() == l_gameObject;
                       });
11-9. STL の使い方
     ・要素の追加は emplace_back、map への追加は try_emplace、存在の確認は contains を使い、追加する前に reserve します。
     ・要素の削除は std::erase_if、検索は std::ranges::find / any_of / find_if を使います。
     ・オブジェクトの生成は std::make_shared / std::make_unique を使い、new は使いません。
     ・文字列の整形には std::format を使います。
     ・外部ライブラリの型が決めている場合だけ、次の書き方を使って構いません。
         ImVector(ImGui)の要素の追加 → push_back(ImVector には emplace_back がないため)
         Jolt の参照カウント付きのオブジェクト(JPH::Ref / DebugRenderer::Batch など)の生成 → new(Jolt が delete するため)
11-10. 次のものは使いません。
       例外(try / throw) / goto / typedef / mutable / [[nodiscard]] / using namespace / this->
     ・this-> は、テンプレートの基底クラスのメンバを呼ぶとき(基底クラスがテンプレート引数で決まる場合)だけ使います。
       この場合は this-> がないとコンパイルできないためです(DirectAndComputeCommandListBase)。
       テンプレートではないクラスでは、this-> を書かずに呼びます。
     ・nullptr との比較の結果を bool に入れるときも == nullptr / != nullptr は書かず、static_cast<bool>(...) にします。
         const bool l_isDragging = static_cast<bool>(ImGui::GetDragDropPayload());
11-11. 取得関数(GetREF / GetMutableREF / GetVAL など)を続けて呼ぶ書き方はしません。1段ずつ変数で受けます。
     ・weak_ptr を取り出す GetVALXxx().lock() の形だけは、続けて書いて構いません。
         NG : auto& l_cameraContext = l_graphicsManager.GetMutableREFRenderer().GetMutableREFCameraContext();
         OK : auto& l_renderer      = l_graphicsManager.GetMutableREFRenderer();
              auto& l_cameraContext = l_renderer.GetMutableREFCameraContext  ();
         OK : const auto& l_scene = l_sceneManager.GetVALScene().lock();
     ・シングルトンの GetInstance() の後ろにも、取得関数を続けて書きません。先にシングルトンを変数で受けます。
         NG : const auto& l_scene = SceneManager::GetInstance().GetVALScene().lock();
         OK : const auto& l_sceneManager = SceneManager::GetInstance ();
              const auto& l_scene        = l_sceneManager.GetVALScene().lock();


================================================================================
 第12章 エラー処理とログ
================================================================================

12-1. エラーの判定には FWK_ASSERT_RETURN_IF / FWK_ASSERT_RETURN_VALUE_IF を使います。assert() は直接書きません。
     IF が付かない FWK_ASSERT_RETURN / FWK_ASSERT_RETURN_VALUE は、直前の if で判定を済ませている場合だけ使います。
         FWK_ASSERT_RETURN_IF(!l_rootSignature, "PhysicsDebugPass用RootSignatureが無効のため、PhysicsDebugPassの実行に失敗しました。");
12-2. メッセージの書き方
     ・日本語で書き、最後に句点「。」を付けます。
     ・「{原因}のため、{処理}に失敗しました。」の形で書きます。
         "Deviceが無効のため、ImGuiの初期化処理に失敗しました。"
         "コマンドアロケータの作成に失敗しており、リセット処理に失敗しました。"
     ・補足の情報は改行して「項目名 : {}」の形で付けます: "...に失敗しました。\nFilePath : {}"
12-3. FWK_ADD_LOG の色は次のように使い分けます。
       警告: Constant::k_imguiDebugWarningColor
       成功: Constant::k_imguiDebugSuccessColor
       情報: Constant::k_imguiDebugINFOColor
12-4. D3D12 / COM の HRESULT は次のように確認します。
         auto l_hr = l_device->CreateCommandQueue(&l_desc, IID_PPV_ARGS(m_commandQueue.ReleaseAndGetAddressOf()));

         FWK_ASSERT_RETURN_VALUE_IF(FAILED(l_hr), "コマンドキューの作成に失敗しました。", false);
12-5. 成功・失敗を返す関数(Create / Load / Save / Resize など)は bool を返します。
     失敗したときの戻り値は、bool なら false、weak_ptr や構造体なら {}、ID なら k_invalidXxx にします。


================================================================================
 第13章 ポインタ・引数・所有権
================================================================================

13-1. 所有するものは std::shared_ptr / std::unique_ptr で持ち、参照するだけのものは std::weak_ptr のメンバ(m_owner / m_parent など)で持ちます。
13-2. 生ポインタは、「見つからないかもしれない参照」を返す FindPTRXxx / FetchPTRXxx の戻り値と、外部 API とのやり取りにだけ使います。
13-3. 自分自身を他に渡すクラスは std::enable_shared_from_this を継承し、weak_from_this() を渡します。
13-4. 引数の渡し方は、型の大きさで決めます。
     ・8バイト未満の型(bool / float / int / UINT / std::uint32_t / DWORD / 列挙型 / DescriptorIndex など)は
       const の値渡しにします: const float a_value / const Enum::XxxType a_type
     ・8バイト以上の型は、数値であっても const 参照で渡します。
         const std::size_t& a_index / const UINT64& a_bufferSize / const double& a_timeSecond /
         const D3D12_GPU_VIRTUAL_ADDRESS& a_gpuVirtualAddress / const boost::uuids::uuid& a_uuid /
         const std::string_view& a_key / const TypeAlias::Math::Vector3& a_position
     ・クラス型・構造体は const 参照で渡します: const std::filesystem::path& a_filePath
     ・生ポインタ / HANDLE / HWND は参照にせず、そのまま値で渡します: const ufbx_node* a_fbxNode
     ・外部ライブラリが型を決めている関数(Jolt の JPH::Vec3Arg / JPH::ColorArg、ウィンドウプロシージャの WPARAM / LPARAM など)は、
       その型のまま受け取ります。
     ・所有権を移すときだけ T&& で受け取り、呼び出し側で std::move します。
         DestroyGameObjectCommand(std::vector<Struct::DestroyedGameObjectRecord>&& a_destroyedGameObjectRecordList);
     ・渡された中身を読むだけのとき、または自分の型へ変換して保持するだけのときは、T&& にせず const 参照で受け取ります。
       この場合、呼び出し側も std::move は書きません。
         CreateGameObjectCommand(const std::vector<std::weak_ptr<GameObject>>& a_createdGameObjectList);
         l_undoRedoSystem.PushUndoCommand<CreateGameObjectCommand>(l_createdList);
     ・スマートポインタは第1章 1-4 のとおりです。
13-5. 引数は、修飾子の種類ごとに次の順で並べます(詳しくは第20章 20-4)。
       const 参照 → const ポインタ → const 値 → 参照 → 右辺値参照(T&&) → ポインタ → 値 → デフォルト引数
13-6. 出力用の参照引数には a_outXxx という名前を付けることがあります(a_outUUIDList)。


================================================================================
 第14章 Definition 層
================================================================================

14-1. 定数(Constant)
         #pragma once

         namespace FWK::Constant
         {
             inline constexpr float k_editorCameraDefaultMoveSpeed   = 5.0F;
             inline constexpr float k_editorCameraDefaultRotateSpeed = 0.005F;
         }
     名前の衝突を避けるため、名前に使うクラスの名前を含めます(k_gameObjectJsonConverterNameJsonKey)。
14-2. 列挙型(Enum)
         namespace FWK::Enum
         {
             enum class RenderGraphShadowMapType
             {
                 Invalid,
                 None,
                 Cascade,
                 Count,
             };

             FWK_JSON_SERIALIZE_ENUM
             (
                 RenderGraphShadowMapType,
                 FWK_JSON_ENUM_VALUE(RenderGraphShadowMapType::Invalid),
                 FWK_JSON_ENUM_VALUE(RenderGraphShadowMapType::None),
                 FWK_JSON_ENUM_VALUE(RenderGraphShadowMapType::Cascade),
                 FWK_JSON_ENUM_VALUE(RenderGraphShadowMapType::Count),
             )
         }
     ・最初の値は Invalid(または None)にし、要素数が必要な場合は最後に Count を置きます。
     ・JSON に保存する列挙型は、すぐ後ろに FWK_JSON_SERIALIZE_ENUM を書きます。
     ・ビットフラグは XxxBitShiftFlag : std::uint32_t { Invalid = 0U, X = 1U << 0U, Y = 1U << 1U, ... } の形で書きます。
     ・インスペクタで文字列から選ぶ列挙型は、namespace の外に次の登録を書きます。
         FWK_REGISTER_STRING_VALUE_BIDIRECTIONAL_REGISTRY(FWK::Enum::Xxx, FWK::Enum::Xxx::Value)
14-3. 構造体(Struct)の書き方は第7章 7-11 のとおりです。置き場所は次のように決めます。
     ・class の中に入れ子で定義してよいのは、そのクラスの中(private)だけで使う構造体だけです。
       public / protected に入れ子の構造体を置くことはしません。外から使う構造体はすべて Definition/Struct に置きます。
     ・ファイルは Source/Framework/Definition/Struct/<分類>/<所有クラス名>Struct.h に作ります。
         分類     : 所有クラスがある最上位のフォルダ名(Graphics / Editor / Physics / Window / Utility / TypeINFO など)
                    同じ種類の構造体がまとまっているフォルダがある場合はそこに入れます(Graphics/Buffer など)。
         ファイル : 1つの所有クラスで使う構造体は、1つのファイルにまとめて書きます。
           例) Window の構造体             → Definition/Struct/Window/WindowStruct.h
               StaticStructuredBuffer の構造体 → Definition/Struct/Graphics/Buffer/StaticStructuredBufferStruct.h
     ・namespace FWK::Struct に書きます。同じ namespace の中で名前が重ならないように、
       ModelMesh / ClientSize のような一般的な名前には所有クラスや機能の名前を頭に付けます。
         StaticModelRecord::ModelMesh       → Struct::StaticModelMesh
         Window::ClientSize                 → Struct::WindowClientSize
         SwapChainJsonConverter::BackBuffer → Struct::SwapChainBackBuffer
       もともと内容が分かる名前(TextureLoadResult / BufferUploadCommand など)はそのままの名前で構いません。
     ・テンプレートクラスの型引数を使う構造体は、template の構造体にします。
         template <typename Type>
         struct SmartPointerVectorListArrayElementData final { ... };
     ・構造体が使う定数は、構造体のヘッダーより前に読み込まれる Definition/Constant に置きます。
       構造体は所有クラスより先に読み込まれるため、所有クラスの static constexpr 定数は使えません。
         Window の k_defaultWindowWidth など → Definition/Constant/Window/WindowConstant.h
     ・Framework.h では、所有クラスのヘッダーの直前に #include します(定数ヘッダーがあればその前)。
     ・フィルターはフォルダと同じ名前にし、まだ無い場合は作ります(Source\Framework\Definition\Struct\Window など)。
     ・テンプレートで複数のクラスを同じように扱うため、所有クラス側から構造体を同じ名前で参照する必要がある場合は、
       所有クラスの public に型の別名を置きます。
         using ModelVertex = Struct::StaticModelVertex;
         using ModelMesh   = Struct::StaticModelMesh;
14-4. 型エイリアス(TypeAlias)
         namespace FWK::TypeAlias
         {
             using DescriptorIndex = std::uint32_t;
         }
     ・ファクトリーは using XxxSharedFactory = GenericFactory<std::shared_ptr<XxxBase>>; の形で定義します。
     ・数学の型は TypeAlias::Math::Vector3 / Matrix / Quaternion / Color(DirectX::SimpleMath)を使います。
14-5. Concept
         namespace FWK::Concept
         {
             template <typename Type>
             concept IsDerivedPipelineStateBaseConcept = IsDerivedBaseConcept<Type, Graphics::PipelineStateBase>;
         }
14-6. マクロは do { ... } while (false) で囲み、行末の \ の位置を揃えます。


================================================================================
 第15章 シリアライズ(Converter)とインスペクタ
================================================================================

15-1. JSON への変換は専用のクラスに分け、本体のクラスはそれをメンバに持って処理を任せます。
         namespace FWK
         {
             class Window;
         }

         namespace FWK::Converter
         {
             class WindowJsonConverter final
             {
             public:

                  WindowJsonConverter() = default;
                 ~WindowJsonConverter() = default;

                 void Deserialize(const nlohmann::json& a_rootJson, Window& a_window) const;

                 nlohmann::json Serialize(const Window& a_window) const;

             private:

                 static constexpr std::string_view k_styleTagJsonKey = "StyleTag";
             };
         }
     ・置き場所は <機能>/Converter/Json/、名前空間は FWK::Converter で、関数には const を付けます。
     ・JSON のキーは private の static constexpr std::string_view k_xxxJsonKey として定義し、値は PascalCase の英語にします。
       複数の Converter で共有するキーは Definition/Constant に置きます。
15-2. Deserialize は次のように書きます。
         void FWK::Converter::WindowJsonConverter::Deserialize(const nlohmann::json& a_rootJson, Window& a_window) const
         {
             if (a_rootJson.is_null()) { return; }

             const Enum::WindowStyle l_windowStyle = a_rootJson.value(k_styleTagJsonKey, Enum::WindowStyle::Normal);

             a_window.SetStyle(l_windowStyle);
         }
     ・値は a_rootJson.value(k_key, 既定値) で読み込みます。
     ・子の JSON は if の初期化文で取り出します。
         if (const auto& l_json = a_rootJson.value(k_key, nlohmann::json{});
             !l_json.is_null())
     ・配列は Utility::IsJsonArray(a_rootJson, k_key) で確認してからループします。
15-3. Serialize は次のように書きます。
         nlohmann::json FWK::Converter::WindowJsonConverter::Serialize(const Window& a_window) const
         {
             nlohmann::json l_rootJson = {};

             l_rootJson[k_styleTagJsonKey] = a_window.GetVALStyle();

             return l_rootJson;
         }
     ・Vector3 / Color / UUID などは Utility::SerializeXxx / DeserializeXxx を使います。
     ・ファクトリーから生成する型は Utility::SerializeInstanceType / DeserializeInstanceType を使います。
15-4. CONFIG の読み込みは次のように書きます。
         const auto& l_rootJson = Utility::LoadJsonFile(k_configFileIOPath);

         if (l_rootJson.is_null()) { return; }

         m_jsonConverter.Deserialize(l_rootJson, *this);
     保存は SaveCONFIG() const の中で Utility::SaveJsonFile(m_jsonConverter.Serialize(*this), k_configFileIOPath) を呼びます。
15-5. インスペクタ
     ・<機能>/Inspector/XxxInspector に void EditInspector(Xxx& a_xxx) を作り、本体の EditInspector から呼び出します。
     ・画面に表示する文字列は private の static constexpr std::string_view k_xxxLabel = "日本語"; として定義します。
     ・ImGui の ID は "##ClassName" の形の定数にします。
       アイコンだけのボタンは、アイコンの後ろに ID を続けた1つの定数にします。
         static constexpr std::string_view k_clearSearchButtonLabel = "\xEF\x80\x8D##DetailsEditorGameObjectAddComponentClearSearch";
       幅を計算するときは ImGui::CalcTextSize(ラベル, nullptr, true) として、"##" より後ろを幅に含めません。
     ・ImGui の Push / Begin と Pop / End は必ず対にし、途中で return する場合もその前に End / Pop を呼びます。


================================================================================
 第16章 コメント(.cpp・HLSL)
================================================================================

16-1. コメントは // の後に半角スペースを1つ入れて書きます。/* */ は空の仮想関数の決まった文にだけ使います。
16-2. 行末にはコメントを書かず、対象の行の直前に書きます。
16-3. コメントは日本語で書きます。
     ・です・ます調は使わず、常体か体言止めで書きます。
     ・句点「。」は基本的に付けません。
16-4. .cpp のコメントは詳しく書きます。処理のまとまりごとに「何をするのか」「なぜそうするのか」を書いてください。
16-5. 外部 API を呼び出すときは、関数名と各引数の意味を縦に並べて説明します。
         // CreateCommandQueue(コマンドキューの設定内容、
         //                    受け取りたいCOMインターフェース型のID、
         //                    作成結果のポインタを書き込むアドレス);
16-6. 注意書きは // ※注意 / // ※ 注意 :、具体例は // 例 :、未完了の箇所は // TODO で書き始めます。
16-7. D3D12 の Desc 構造体は「コメント → 1つのフィールドへの代入 → 空行」を繰り返して、1つずつ設定します。
         D3D12_COMMAND_QUEUE_DESC l_desc = {};

         // このコマンドキューで実行するコマンドリストの種類を指定する
         l_desc.Type = CommandType;

         // コマンドキューの優先度を指定する
         l_desc.Priority = D3D12_COMMAND_QUEUE_PRIORITY_NORMAL;
16-8. ヘッダーの関数の外側にはコメントを書きません(第1章 1-1)。
      ただし、テンプレートや inline のようにヘッダーに処理の本体を書かなければならない関数(Utility の inline 関数など)の中は、
      初学者でも分かるように .cpp と同じ詳しさでコメントを書きます。
        ・関数の最初に、その関数が「何をするのか」「引数と結果がどういう意味か」を書きます。
        ・weak_ptr の lock()・イテレータ・再帰呼び出し・stable_sort などの、初学者がつまずきやすい書き方には理由を書きます。
        ・並べ替えのように手順がある処理は、「1. ~ 2. ~」と番号を付け、具体的な例(例 : ...)を添えます。
        ・関数の宣言(シグネチャ)の前や、行末にはコメントを書きません。


================================================================================
 第17章 テンプレートとコンセプト
================================================================================

17-1. template <typename Type> の次の行に、4文字下げて requires を書きます。
     または template <Concept::IsDerivedXxxConcept Type> のように Concept を直接書きます。
         template <typename Type>
             requires std::is_enum_v<Type>
         class Observer final
17-2. requires の条件が複数あるときは1行に1条件ずつ書き、&& / || は行末に置きます。
17-3. メンバ関数ごとの制約は、関数宣言の次の行に requires を書きます。
         void Add(const Type& a_type)
             requires k_isWeakPTR
17-4. コンパイル時の分岐には if constexpr を使い、前提条件の確認には static_assert(条件, "日本語のメッセージ") を使います。


================================================================================
 第18章 型情報・ファクトリー・JSON による登録
================================================================================

18-1. 多態的に扱うクラスは、基底クラスに FWK_DEFINE_TYPE_INFO_ROOT、派生クラスに FWK_DEFINE_TYPE_INFO を付けます。
18-2. JSON の型名から生成するクラスは、ヘッダーの末尾(namespace の外)で FWK_REGISTER_FACTORY_METHOD を使って登録します。
18-3. 型の情報は Xxx::GetREFTypeINFO().k_staticTypeID / GetREFRuntimeTypeINFO() で取得します。
18-4. RenderGraph のパス・DrawRequest・Uploader は、Framework/CONFIG/Graphics/GraphicsCONFIG.json で宣言して登録します。
18-5. 描画パスでは、コンストラクタの中で SetupExecutionLayer と Read / Write(RenderTarget / DepthStencil / ShadowMap)を宣言します。
     ・プレビューなど、メイン以外のビューでも実行するパスは、SetupViewScope(Enum::RenderGraphPassViewScope::AllViews) を宣言します。
       宣言しないパスは、メインビューだけで実行されます(エディター専用のパスが、プレビューへ混ざらないようにするためです)。
     ・ビューごとに内容が変わる定数バッファ(カメラ・カスケードの行列・FinalColor など)のアップローダーは、
       固定位置(DynamicConstantBufferFixedWritePositionUploaderBase)ではなく、書き込み位置を進める方式
       (DynamicConstantBufferAdvancingWritePositionUploaderBase)にします。
       CreateCount(GraphicsCONFIG.json)には、「1フレームで書き込む回数 × ビューの数」以上の値を書きます。
       固定位置だと、後から書いた別のビューの値を、GPU が先に描いたビューでも読んでしまうためです。
18-6. 頂点バッファ(VB)・定数バッファ(CB)の構造体は、用途ごとに専用のものを作り、他のパスの構造体を再利用しません。
     ・中身が同じでも、別の名前の構造体にします(VBPhysicsDebug と VBEditorCameraDebug など)。
       片方だけを変更したときに、もう片方の描画が壊れるのを防ぐためです。
     ・パイプラインステートなどを共有していて、レイアウトを合わせる必要がある場合は、static_assert で大きさの一致を確認します。
18-7. 派生クラスのインスタンスを「型」で取り出す仕組みは、次の形で作ります(EditorManager / RenderGraph が先例です)。
     ・所有は std::vector<std::shared_ptr<XxxBase>> の XxxList、検索用は
       std::unordered_map<TypeAlias::StaticTypeID, std::weak_ptr<XxxBase>> の XxxMap(private の using)で持ちます。
     ・登録は AddXxx(const std::shared_ptr<XxxBase>&) で、List に加えて Map に k_staticTypeID をキーとして登録します。
     ・取り出しはテンプレートの FindVALXxx<Type>() で、Type::GetREFTypeINFO().k_staticTypeID で探し、
       lock() してから std::static_pointer_cast<Type> で返します。見つからないときは {} を返します。
         template <Concept::IsDerivedEditorWindowBaseConcept WindowType>
         std::weak_ptr<WindowType> FindVALWindowEditor() const
     ・dynamic_cast は使いません(11-6)。テンプレート引数は Concept で XxxBase の派生に制限します。


================================================================================
 第19章 HLSL
================================================================================

19-1. 文字コードは BOM 付きの UTF-8 にします。.hlsli には #pragma once ではなくインクルードガードを書きます。
         #ifndef MODEL_HLSLI
         #define MODEL_HLSLI
         ...
         #endif // MODEL_HLSLI
19-2. 定数は static const で書き、k_ を付けます。float には F、uint には U を付けます。
         static const uint k_modelMeshShaderThreadCountX = 32U;
19-3. cbuffer は CBXxx : register(bN) と書きます。メンバには g_ を付け、型と名前の位置を揃えます。
     行列は row_major matrix にします。C++ 側の CBXxx 構造体と、並び順とパディングを一致させてください。
19-4. ローカル変数には l_、引数には a_ を付け、const を付けます。構造体のメンバはプレフィックスなしの lowerCamelCase にします。
19-5. エントリポイントは void main(...) とし、[numthreads(k_xxxX, k_xxxY, k_xxxZ)] も定数で書きます。
19-6. リソースは Bindless で参照します。
         StructuredBuffer<T> l_buffer = ResourceDescriptorHeap[g_xxxSRVDescriptorIndex];
19-7. 書式は C++ と同じです(Allman スタイル、1行 if、縦揃え、日本語のコメント)。
     C++ 側と値を一致させる必要がある定数には、そのことをコメントで書いておきます。

 第20章 宣言と引数の並び順
================================================================================

20-1. 並び順の基本は「配列 → ポインタ → 値」です。
       1. 配列        std::vector / std::unordered_map / std::unordered_set / std::array / std::deque などの
                      要素をまとめて持つ型(XxxMap / XxxList などの型エイリアスも含みます)
       2. ポインタ    std::unique_ptr / std::shared_ptr / std::weak_ptr / ComPtr / 生ポインタ / HANDLE / HWND
       3. 値          上の2つ以外のすべて
     値の中の順番は、メンバ変数・定数・引数ごとに 20-2 ~ 20-4 のとおりです。
     ・値の中のクラスと構造体は、型を定義している場所によって、ヘッダーの上から次の順に並べます。
         外部APIのクラス → std のクラス → 自作クラス → 外部APIの構造体 → std の構造体 → 自作の構造体
       外部APIのクラス   nlohmann::json / DirectX::ScratchImage / JPH::BodyID など
       std のクラス      std::string / std::wstring / std::string_view / std::filesystem::path / std::chrono の型 など
       自作クラス        Scene / Device / XxxSystem / XxxPane など(Converter / Inspector はこの最後)
       外部APIの構造体   boost::uuids::uuid / TypeAlias::Math の型(DirectX::SimpleMath) / ImVec2 / RECT /
                         D3D12 の DESC などの構造体 / DirectX::TexMetadata など
       std の構造体      std::pair / std::source_location など
       自作の構造体      Struct::Xxx / クラスの中の private の構造体 など
     種類が変わるところで空行を入れます。
20-2. メンバ変数(m_)
       1. 配列
       2. ポインタ
       3. 外部APIのクラス
       4. std のクラス
       5. 自作クラス
       6. Converter / Inspector
       7. 外部APIの構造体
       8. std の構造体
       9. 自作の構造体
      10. 列挙型
      11. 数値
      12. bool
          std::vector<std::shared_ptr<GameObject>> m_gameObjectList = {};

          std::weak_ptr<GameObject> m_owner = {};

          nlohmann::json m_json = {};

          std::string m_name = {};

          SceneChanger m_sceneChanger = {};

          Converter::SceneJsonConverter m_jsonConverter = {};

          boost::uuids::uuid m_uuid = {};

          Struct::XxxState m_state = {};

          Enum::XxxType m_type = Enum::XxxType::Invalid;

          std::uint32_t m_count = k_initialCount;

          bool m_isEnable = false;
     ・Converter と Inspector の順番は決めていません。
20-3. 定数(クラスの static constexpr と Definition/Constant の inline constexpr)
       1. 配列(std::array / C 配列)
       2. ポインタ
       3. 文字列(std::string_view / char / wchar_t)などの std のクラス
       4. 数学の型(Color / Vector / ImVec2 など)などの外部APIの構造体
       5. 列挙型
       6. 浮動小数点(float / double)
       7. 64ビットの整数(std::size_t / UINT64 / std::uint64_t)
       8. 32ビットの整数(UINT / std::uint32_t / DWORD)
       9. 16ビットの整数(std::uint16_t)
      10. 8ビットの整数(std::uint8_t)
      11. int
      12. bool
     ・ファイルパス(std::filesystem::path)の位置は決めていません。
20-4. 引数(a_)
     ・まず修飾子の種類で、次の順に並べます。
       1. const 参照        const T& / const std::weak_ptr<T>& / const nlohmann::json& / const std::size_t&
       2. const ポインタ    const T*
       3. const 値          const bool / const Enum::XxxType / const float / const UINT
       4. 参照              T&(出力や変更する対象)
       5. 右辺値参照        T&&(所有権を受け取るもの)
       6. ポインタ          T*
       7. 値                const の付かない値渡し
       8. デフォルト引数
     ・同じ種類の中は、次の順に並べます(3 ~ 8 は 20-1 の型の定義場所による順番です)。
        1. 配列(std::vector / std::unordered_map / std::unordered_set / std::array / std::deque など。範囲は 20-1 のとおりです)
        2. スマートポインタ(std::weak_ptr / std::shared_ptr / std::unique_ptr など)
        3. 外部APIのクラス(nlohmann::json など)
        4. std のクラス(std::string / std::filesystem::path など)
        5. 自作クラス
        6. 外部APIの構造体(boost::uuids::uuid / 数学の型 / D3D12 の構造体 など)
        7. std の構造体
        8. 自作の構造体
        9. 列挙型
       10. 数値
       11. bool
          void Load(const std::filesystem::path& a_filePath, const Device& a_device, const GPUMemoryAllocator& a_gpuMemoryAllocator);
          RenameGameObjectCommand(const std::string& a_beforeName, const std::string& a_afterName, const boost::uuids::uuid& a_gameObjectUUID);
          std::size_t FetchVALXxxRank(const std::unordered_map<boost::uuids::uuid, std::size_t>& a_rankMap, const std::weak_ptr<GameObject>& a_gameObject);
          void Xxx(const std::vector<std::weak_ptr<GameObject>>& a_gameObjectList,
                   const std::weak_ptr<GameObject>&              a_parent,

                         std::vector<boost::uuids::uuid>&&       a_uuidList);
20-5. ローカル変数(l_)は、使う順番(依存される側が先)に宣言します。
20-6. 次の場合は 20-1 ~ 20-5 の順番より優先し、規約違反とはしません。
     ・デストラクタが実行される順番や、初期化の順番を守るための並び
       (メンバ変数は宣言の順番で初期化され、逆の順番で破棄されます。
        依存される側を先に宣言する必要がある場合は、その順番を優先します)
     ・デフォルト引数を使うための並び(デフォルト引数は後ろにしか置けないため)
     ・可変長引数(パラメータパック)は最後に置きます。
     ・後ろの定数が前の定数を使っている場合(配列の要素数など)
     ・外部ライブラリの基底クラスをオーバーライドする関数や、外部 API に渡すコールバック関数と、
       その引数の並びに合わせて作った関数
       (JPH::DebugRenderer の DrawGeometry / DrawText3D / CreateTriangleBatch、ウィンドウプロシージャなど)
     ・ポインタと要素数の組(a_vertexList と a_vertexCount など)は、組のまま続けて並べます。
     ・GPU のメモリ配置に合わせる構造体(CBXxx / VBXxx と、その中に入れる構造体)のメンバ


================================================================================
 第21章 コードを書いたときのチェックリスト
================================================================================

[ ] BOM 付き UTF-8 / CRLF / 末尾に改行なし / インデントはスペース4つ
[ ] ヘッダーは #pragma once のみで、#include とコメントはなく、前方宣言は別の namespace ブロックに書いている
[ ] namespace FWK::Xxx のネスト記法で書き、.cpp は完全修飾名で定義している(namespace ブロックなし)
[ ] class Xxx final(基底クラスは XxxBase で final なし)、public → private の順、アクセス指定子の前後に空行
[ ] コンストラクタ / デストラクタは「 X() = default;」「~X() = default;」で ~ の位置を揃えている
[ ] public は INIT → Deserialize → Update 系 → Draw → EditInspector → Serialize → その他の処理関数 の順で、その後ろに取得・設定・判定の関数が続く
[ ] 空行なしで隣り合う関数は似た処理だけで、.cpp の定義の順番はヘッダーの宣言の順番と同じ(間に別の関数を挟まない)
[ ] 同じアクセス指定子の中で 処理関数 → Is / Can / Has → Apply → Set → Fetch / Find → GetREF → GetMutableREF → GetPTR → GetMutablePTR → GetVAL の順で、Load / Save と Deserialize / Serialize は空行で離している
[ ] friend は SingletonBase のためだけに使っている
[ ] private は 関数 → static constexpr k_ → m_ メンバ(初期化子は {} / nullptr / 定数) → 型情報マクロ の順
[ ] ヘッダーで定義するものと、リテラルで初期値を与える変数は、auto を使わず型名を書いている
[ ] 8バイト以上の引数は const 参照、8バイト以上のローカル変数は const auto& で受け取っている
[ ] メンバ変数・定数を第20章の順番(配列 → ポインタ → 値)で、引数を修飾子の順番(const 参照 → const ポインタ → const 値 → 参照 → 右辺値参照 → ポインタ → 値)で並べている
[ ] 変数は l_ / 引数は a_ / メンバは m_ / 定数は k_(直後は小文字)、Setter の引数は a_set
[ ] GetREF / GetMutableREF / GetVAL / FetchVAL / FindPTR を使い分け、略語は大文字(REF VAL PTR ITR INFO UUID ID MIN MAX など)
[ ] 引数が4個以上の宣言・呼び出しは1行に1引数ずつ書き、位置を揃えている(3個以下は1行で書いている)
[ ] クラス・構造体のメンバ・引数・定数を「外部APIのクラス → std のクラス → 自作クラス → 外部APIの構造体 → std の構造体 → 自作の構造体」の順で並べている
[ ] 続けて並ぶ = と ( を縦に揃え(std::min などが混ざっても揃える)、const 付きと const なしの宣言は型の位置を揃えている
[ ] { } の初期化子は、要素が4つ以上なら縦に並べ、3つ以下なら1行に書いている
[ ] 型名を書いて値を作るときは ImVec2{ x, y } のように { } を使っている(コンテナ・文字列は除く)
[ ] Allman スタイル、波括弧は必ず付け、return / continue の1文だけは1行 if で書いてよい(break や他の文はブロック)、else は改行
[ ] && / || は1行に1条件、演算子は行末で、演算子の前の空白は1つ(演算子の位置は揃えない)
[ ] return の前、FWK_ASSERT の後、1行 if の後(1行 if が続くときは詰めて { を揃える)、文の種類が変わるところに空行がある
[ ] 変数の宣言が続くところに空行を入れず、const の有無で6文字ずらして型・名前・= ・( を揃えている
[ ] 空行を2行以上続けていない
[ ] bool を返す判定の関数は Is / Can / Has で始まっている(Contains などを使っていない)
[ ] 数値はすべて k_ の定数(接尾辞は大文字の F / U / ULL)、文字列は std::string_view の定数
[ ] エラーは FWK_ASSERT_RETURN(_VALUE)_IF で判定し、メッセージは「〜のため、〜に失敗しました。」
[ ] weak_ptr は先頭で lock() して if (!l_x) { return; } で確認している
[ ] .cpp のコメントは // + 日本語の常体で、行末コメントはなく、コメントの前に空行がある
[ ] Converter / Inspector をメンバに持って処理を任せ、JSON のキーは k_xxxJsonKey にしている
[ ] 新しいファイルを vcxproj / filters / Framework.h に登録している
[ ] ファイル名とクラス名が大文字・小文字まで同じで、Definition のファイルには Constant / Enum などの種別が付いている
